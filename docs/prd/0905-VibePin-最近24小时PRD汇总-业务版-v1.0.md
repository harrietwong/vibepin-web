# VibePin 最近24小时 PRD 汇总（业务版）v1.1

> 面向：业务负责人、产品负责人及验收负责人  
> 原汇总窗口：2026-09-04 21:59 至 2026-09-05 21:59（America/New_York）；2026-09-06增量修订纳入14条业务批注与0906 Bug审查报告。  
> 当前结论：需求和验收口径已汇总；历史环境已有部分只读界面观察与代码测试证据，但本次整理未重测。本批需求尚未全部实现，当前最终环境也尚未全部完成两轮验收；正式环境放行仍不成立。

## 一、这24小时要解决什么

VibePin 的核心承诺不是“界面看起来能发布”，而是帮助商家从选商品、准备素材、生成内容、选择账号和版位，到排期或发布，始终知道内容是否真实可用、会发往哪里、额度会不会被多扣，以及失败后下一步怎么做。本轮汇总来自时间窗口内被修改的 PRD、最近验收会话记录和媒体安全补充要求；文中按当前目录引用开发过程产物、PRD 与素材。

本版只讲业务结果和验收标准，不把“方案已写”“代码存在”“历史截图曾通过”写成“今天已经修好”。历史截图证明曾发生过问题；后续每项必须在同一个最终测试环境，以实际操作、实际页面、必要的状态回读和截图重新证明。任何旧分支的测试通过，也不能证明新环境已经完成。

本轮按四个原则推进：

1. 先堵住会错发、串号、重复扣费、看似成功实则失败的风险，再提升页面美观和效率。
2. `Schedule`（排期）是 Studio 的主操作；`Publish now`（立即发布）是次级操作。排期保存成功只代表 VibePin 已记住计划，不代表到点后第三方已发布成功。
3. 标题、描述、Website URL 默认是可选能力；只有某个平台、某种发布动作明确要求时，才在该字段旁提示必填。Pinterest 在需要时必须选择 Board；其他平台不应被 Pinterest 规则误伤。
4. 已发布成功的历史记录必须保留；之后的新失败另行显示，不能倒过来把历史成功擦掉，也不能把一次成功腿伪装成全部成功。

## 二、建议处理顺序

**第一批：先止损（P0）**。登录和回跳、付款测试、商品与灵感加载、生成与额度、草稿隔离、发布目标、发布状态、排期、重试、滚动可达性、设置假成功、键盘与模态基础能力，必须先完成。它们直接影响收入、内容产出、跨账号安全或第三方错发。

**第二批：让日常运营顺手（P1）。AI与上传双入口、统一图片失败状态、筛选与去大标题、Plan、批量编辑、公共页偏好、路由与性能、全局视觉和交互连续性。核心操作不可点击或可能错发时按阻断问题优先处理。**

**第三批：精修体验（P2）**。Contact 成功页等不阻塞业务的界面细节，在前两批稳定后收尾。

建议按“事实和归属 → 可恢复流程 → 页面呈现 → 跨页回归”实施：先确认谁的内容、哪个目标、哪个状态、是否已扣额度；再完成修复和重试；最后统一视觉与动画。不得因为先做了漂亮页面，就跳过状态、隐私和第三方回执。

## 三、50项业务改进台账

### A. Studio、草稿与创建内容

**FB-0905-01｜失败图片仍显示粉色占位且状态不统一**

- 问题：失败卡仍可能显示粉色假图，或在粉色、深灰、破图等多套失败样式之间切换，用户看不出真实产出与失败状态。
- 用户影响：失败被伪装成有图片或成功，用户无法判断能否编辑、重试和发布；如核查发现素材串号，另按P0处理。
- 准备怎么改：优先统一生成失败、媒体读取失败、过期和不可用状态。没有有效成品的失败卡不得继续显示粉色测试图、旧图或品牌色假图，统一进入与原因匹配的失败预览。
- 准备怎么改：正常上传和正常生成的有效图片按原样显示；失败回退由任务结果和媒体有效性决定。已发布历史成品仍可在历史区域展示，但不能冒充本次失败生成的成品。
- 业务边界：切换内容 A→B→A 时必须重新读取对应素材，不能把前一张图残留到后一张卡；不在页面、截图或日志暴露私有原图地址。
- 验收看什么：生成失败、读图失败、旧粉色占位、404、解码失败、超时、重试成功和A→B→A各两轮；失败样式一致，成功后恢复真实图片，不出现粉色假图或串图。

**FB-0905-02｜失败图片占位过于粗糙**

- 问题：失败图片被展示成整块深灰色，既像空白卡片又像内容加载完成，用户难以判断该图片能否继续使用。
- 用户影响：运营人员会反复点击、等待或误以为内容已经生成，降低对 Studio 状态的信任。
- 准备怎么改：按UI设计审查使用中性预览底板、统一小图标、明确失败原因和可操作入口；缩减失败卡无内容大色块，使桌面100%缩放时媒体、状态、字段和动作有稳定层级。
- 准备怎么改：不再使用粉紫宣传式渐变，不显示破图符号、原始文件名或永久转圈；弱动效在减少动效设置下自动收敛。
- 业务边界：占位只是提示，不得伪装成真实图片；卡片尺寸在加载、失败和重试时保持稳定，避免页面跳动。
- 验收看什么：桌面浏览器100%缩放下检查1440×900、1280×800、1007×632，移动390×844各两轮；无需缩小浏览器才能看清卡片。检查首屏密度、状态文字、操作热区、卡片高度稳定、无粉色假图和永久spinner。

**FB-0905-03｜失败卡片出现重复 Edit**

- 问题：历史页面中同一失败卡可能连续出现两个 `Edit`，用户不知道两者是否编辑同一内容或会触发不同副作用。
- 用户影响：误点可能编辑错 Pin，也会让团队对重试、改目标和普通编辑的区别失去判断。
- 准备怎么改：每张卡只保留一个明确归属的编辑入口，例如“编辑：内容标题”；重试、改 Board 与编辑保持三个不同动作。
- 准备怎么改：取消编辑不保存未确认修改；打开哪张卡，焦点和编辑对象就必须始终是哪张卡。
- 业务边界：减少按钮不等于合并业务含义，不能把修复发布目标偷偷做成普通编辑，也不能让编辑自动重新发布。
- 验收看什么：连续检查10张失败卡，视觉和读屏均每卡只有一个 Edit；取消、保存、键盘打开和跨卡切换各两轮，无误编辑和重复项。

**FB-0905-04｜批量发布目标与单条不一致**

- 问题：批量编辑的“发布到”与单张卡的目标选择不一致，且用户可能没有完成目标选择的路径。
- 用户影响：批量按钮存在点不开、按钮对应错误动作、目标无法选择等问题，运营无法完成操作，也可能漏选账号或选错Board。
- 准备怎么改：逐个核查批量选择、编辑、保存、取消、发布所选、排期、目标与Board按钮的可点击区域、禁用原因和实际handler；鼠标、键盘和触控结果一致。单条与批量共用账号及其Board/Page规则。
- 准备怎么改：没有可用目标时必须阻止发布，并给出“选择发布目标”的直接入口，而非只显示禁用按钮。
- 业务边界：不能默认回退到某个 Pinterest 账号或 Sandbox Board；批量中已发布、未知状态的目标不得被覆盖。
- 验收看什么：按钮清单逐项记录显示文案、选中数量、启用条件、点击后的真实动作及保存结果；同账号、多账号、平台混选、目标缺失/失效、逐行修复各两轮；编辑不发布，发布不进入普通编辑。

**FB-0905-05｜批量发布时间看似必填**

- 问题：Batch Edit 中时间字段一直展开，用户会误以为必须立即填写时间，影响单纯编辑内容或目标的效率。
- 用户影响：用户可能随手填错时间，或放弃批量操作，造成排期混乱和不必要的学习成本。
- 准备怎么改：发布时间默认收起并清楚标记为“可选”；只有选择排期或主动展开时，才显示时间、时区和相关校验。
- 准备怎么改：编辑内容、修复目标、立即发布和设置未来时间必须是可区分的业务意图，不能共用含糊的按钮。
- 业务边界：未保存的排期编辑关闭即丢弃，不得写入；切回立即发布时应清空未提交的排期时间。取消已经保存的排期必须有明确操作，并通过可信读回确认内容回到未排期，而不是笼统保留旧值。
- 验收看什么：无时间编辑、设置时间、切回立即发布、清除未提交时间、取消已保存排期、改时区、刷新恢复和390px堆叠布局各两轮，确认没有暗中排期。

**FB-0905-06｜AI与上传保留两个明确入口**

- 问题：不同创建方式的入口和后续动作需要重新分组；用户已明确要求AI与上传分开。
- 用户影响：新用户更容易走错路径，老用户会在多个面板之间反复切换并丢失上下文。
- 准备怎么改：顶层保留AI创建与上传两个入口。AI进入商品、创意方向、可选参考和生成设置；上传进入方式选择，再选本地上传、URL导入、商品选择或已支持的其他导入方式。
- 准备怎么改：上传下的各方式复用同一素材归属、校验与草稿保存规则；AI复用相关商品/素材选择组件，但不合并顶层入口。未支持的方式不得展示为可用。
- 业务边界：打开、关闭、切换方式不创建上传、生成任务、额度预留、排期或发布；用户没有确认前只是填写准备信息。
- 验收看什么：分别从AI与上传进入；逐一走本地上传、URL、商品及已支持方式，切换/取消/刷新/换账号各两轮。入口清晰、返回到正确层级、未确认不启动任务、不重复创建草稿。

**FB-0905-07｜全局坏图漏出原始信息**

- 问题：Product、Reference 和 Pin 的坏图可能露出破图标、替代文字或文件名，且各页面表现不一致。
- 用户影响：页面显得不可靠，也可能暴露不应面向客户的内部命名，影响商品判断。
- 准备怎么改：所有业务图片使用统一的加载、成功、失效、超时和回退规则，并在请求前预留图片位置。
- 准备怎么改：局部图片失败只影响这一张图片，提供合适重试或替代提示，不得把整个列表清空或重置。
- 业务边界：图片回退不改变卡片布局，也不把私有原始地址写进浏览器地址、截图和外部分析记录。
- 验收看什么：慢图、404、无法解码、超时、长列表滚动和A→B切换各两轮；桌面、390px无横向溢出、无原始文件名。

**FB-0905-08｜商品选择器标签难懂**

- 问题：`Uploaded`、`Product Ideas` 等标签与图标不能说明图片来自哪里、是否为用户自己的资产、能否放心使用。
- 用户影响：商家无法判断素材的授权和推荐依据，容易把灵感、上传图和商品图混为一谈。
- 准备怎么改：Product 选择器只使用商品来源分类：“我的上传”“URL 导入”“Amazon”“商品灵感”，并为每类展示简短来源依据或更新时间。
- 准备怎么改：Reference 的“为此商品推荐”“通用灵感”等创意分类留在独立 Reference 流程，不混入 Product 来源，也不能伪装成用户手动上传的商品。
- 业务边界：来源标签是业务事实而非装饰，切换账号或工作区后不可复用另一人的素材或说明。
- 验收看什么：我的上传、URL导入、Amazon、商品灵感各两轮，检查来源、筛选和选中结果；再与Reference推荐入口对照，确认两套分类不混淆。

**FB-0905-09｜选品灵感无法加载**

- 问题：选品灵感页面可能直接显示空结果，用户不知道是真的没有机会、仍在加载，还是权限或服务出了问题。
- 用户影响：商家会因空白而错过可售商品，或把数据异常误判断为“市场没有机会”。
- 准备怎么改：明确分开加载中、真实空结果、尚无商品、登录或权限问题、同步失败和可重试服务错误。
- 准备怎么改：所有页面从同一份可靠商品与灵感结果读取，避免不同区域显示相互矛盾的数量或假数据。
- 业务边界：不得用演示数据掩盖异常；重试只刷新灵感，不创建商品、不改动已有选择，也不影响其他账号。
- 验收看什么：加载、真实空集、无商品、401/403、限流、服务错误、超时和重试成功各两轮，核对页面提示与实际结果相符。

**FB-0905-10｜“生成2个 Pin”失败且难以对账**

- 问题：用户请求生成两个 Pin 后可能整体失败，页面又无法说清是哪一步失败、是否已扣额度、是否可以安全重试。
- 用户影响：这是内容生产主链路的直接阻断，且可能造成重复生成、重复计费或用户不敢再试。
- 准备怎么改：先复现并定位两个Pin失败：固定同一商品和请求数量，分别测试手选参考、自动参考和无参考，记录同一次attempt的请求、错误阶段、状态码、requestId及单张结果；不能只换错误文案就关闭问题。
- 准备怎么改：依据复现证据修复真实失败原因，并建立每张图片可追溯的结果和恢复路径。页面显示简短原因与下一步，同一次尝试从进行中更新为唯一终态；本地测试与真实provider验证分开报告。
- 业务边界：失败不结算图片额度；结果未知时先核对，不能盲目再次扣费或重放；重复点击不能创建重复任务。
- 验收看什么：双击、单张失败、全失败、部分成功、响应丢失、刷新恢复和安全重试各两轮，核对成品数、额度、提示和尝试记录一致。

**FB-0905-11｜风格参考图关闭后丢失**

- 问题：用户选好的风格参考图在关闭、重开或失败后可能消失，导致重试时不知道系统将按什么风格生成。
- 用户影响：内容风格不可控，用户会重复选择、重复生成，甚至误认为系统擅自改变了创意方向。
- 准备怎么改：在点击 Generate 前完整保存本次准备信息，包括商品、手选参考、自动参考、创意方向及选择方式。
- 准备怎么改：重新打开、刷新或从失败恢复时，应显示同一次尝试所用设置，并允许用户先修改再重试。
- 业务边界：每份草稿只属于其用户和工作区；换账号、换商品或开启新尝试时不得把旧参考带入。
- 验收看什么：手选参考、自动匹配、关闭重开、失败恢复、刷新、A→B→A和切账号各两轮，确认设置可恢复但不串草稿。

**FB-0905-12｜上传商品图后分析和推荐中断**

- 问题：上传商品图后，后续分析或创意推荐不能稳定完成；换图时也可能迟到显示旧图的建议。
- 用户影响：用户无法从真实商品快速获得方向，只能靠猜或重复上传，拖慢制作速度。
- 准备怎么改：打通上传商品图、商品分析、Keyword Trends信号和数据库候选图片。推荐必须关联当前商品身份、图片版本、关键词/类目、趋势信号时间及真实候选记录，说明图片来自哪里和为何匹配。
- 准备怎么改：商品或图片变化后重新分析和查询；数据库候选、趋势信号及权限分别校验。换图使旧推荐失效，迟到结果不可覆盖；无候选、趋势缺失、数据库失败与分析失败分别显示。
- 业务边界：上传或分析失败不应产生生成额度；用户可看到可行动原因，而不是只有“失败”。
- 验收看什么：用商品A/B和可控数据库候选验证推荐会变化；检查商品图、关键词、趋势和候选记录可追溯。覆盖趋势缺失、候选为空、查询失败、缓存过期、快速换图和刷新两轮；只有通用图库时必须如实标明。

**FB-0905-13｜推荐方向缺少图片依据**

- 问题：创意方向只给一段文字，用户看不出它参考了哪张商品图、哪类灵感，也无法判断建议是否适合自己的商品。
- 用户影响：推荐可解释性不足，用户难以信任或调整方向，容易直接跳过产品价值。
- 准备怎么改：方向卡展示小型可追溯图片、来源、更新时间和“为何适合”的简短业务解释。
- 准备怎么改：用户可查看、替换或关闭自动匹配，不把自动建议写入“我的参考图”或冒充用户选择。
- 业务边界：推荐是辅助，不得在用户未确认时改写商品、参考或已保存创意方向；无匹配结果应诚实说明。
- 验收看什么：有匹配、无匹配、自动匹配、手动替换、过期缓存、服务失败和390px各两轮，确认依据清晰、关闭不影响原选择。

**FB-0905-14｜Creative direction 不像可编辑字段**

- 问题：创意方向区域外观接近普通说明文字，用户不知道能否输入、是否已保存、如何取消修改。
- 用户影响：用户可能错过表达品牌语气和构图意图的机会，或误以为系统已经保存其修改。
- 准备怎么改：把它呈现为清晰的多行输入框，含标签、边界、示例、焦点和编辑中状态。
- 准备怎么改：区分未改、已改未保存、保存中、成功和失败，并提供明确保存或取消；失败保留用户已输入内容。
- 业务边界：未保存创意方向属于私有临时信息，不能塞进可分享链接，也不得跨账号、跨草稿复用。
- 验收看什么：输入、清空、取消、保存失败、保存成功、刷新及键盘操作各两轮；检查焦点、字数和390px不遮挡按钮。

**FB-0905-15｜生成提示前后矛盾**

- 问题：同一次生成可能同时显示“正在生成”的成功色和“未生成”的错误提示，用户无法判断最终状态。
- 用户影响：用户会重复点击或误以为可以离开，增加重复扣费和遗漏结果的风险。
- 准备怎么改：每次尝试只使用一个稳定状态位：开始、处理中、成功、部分成功、失败或未知，状态就地更新。
- 准备怎么改：失败信息靠近相关内容并给出下一步；跨页面完成提醒只保留一条，不与字段错误重复播报。
- 业务边界：未知不是失败，也不是成功；必须保留待核对状态，直到真实结果回来后再结算或允许有依据的恢复。
- 验收看什么：成功、全失败、部分成功、网络中断、页面切换、快速重试和读屏播报各两轮，确认任意时刻只有一个终态。

**FB-0905-18｜Studio 失败提醒反复出现且计数不准**

- 问题：历史大横幅、重复通知和失败数量口径让用户既被打扰，又不知道到底有几条内容需要处理。
- 用户影响：重要失败被噪音淹没，团队也无法用数量判断当天待办和风险。
- 准备怎么改：只保留 Failed 徽标和安静的短提示，以“需要处理的 Pin 数量”作为统一口径。
- 准备怎么改：历史已成功与当前失败分别呈现，避免同一内容同时在成功和失败提醒中重复计数。
- 业务边界：提示不应在每次刷新、切筛选或打开抽屉时重复弹出；用户已处理的失败必须及时退出待办。
- 验收看什么：全成功、全失败、部分成功、历史成功后新失败、筛选切换和刷新各两轮，核对徽标、列表和计数一致。

**FB-0905-19｜Studio 密度、按钮主次混乱**

**FB-0905-20｜Plan 入口不易发现且挤压布局**

- 验收看什么：宽屏、窄屏、390px、键盘、快速开关、返回、刷新和有未保存编辑时关闭各两轮，检查空间与上下文恢复。

### B. 登录、付款、公共页面与套餐

**FB-0905-16｜Google 登录和测试登录失败**

- 问题：Google 授权曾出现错误码，测试内嵌浏览器也不会天然记住用户日常浏览器的 Google 凭据。

- 准备怎么改：分别处理产品授权配置问题和浏览器资料不共享问题；测试环境必须有可用的邮箱密码或 Magic Link 替代路径。

- 验收看什么：邮箱密码、Magic Link、Google 成功、拒绝授权、弹窗未打开和会话保持各两轮；分别在测试浏览器和常用浏览器说明差异。

**FB-0905-17｜Creem 测试付款显示未知错误**

- 准备怎么改：结账前清楚展示 VibePin、套餐、金额、周期和测试标识；错误或过期时返回可恢复页面，允许重新选择但不自动循环创建会话。

- 验收看什么：八种映射各两轮；至少月付与年付各完成两次测试页面到达、取消和错误返回，确认无订阅或额度被错误改变。

**FB-0905-21｜Contact 成功页过于空泛**

- 问题：用户发送联系表单后只看到大空白卡片与两行文字，不知道是否真的送达、何时会收到回复。
- 用户影响：用户可能重复提交，客服收到重复工单，品牌体验也显得不成熟。
- 准备怎么改：提供紧凑成功确认：明确图标、`Message sent`、预计回复时间、返回 VibePin 的主要下一步和必要时的再次联系入口。
- 准备怎么改：成功提示只播报一次，焦点移到成功标题或下一步；不重显刚提交的隐私内容，也不重复提交表单。
- 业务边界：刷新后的语义必须明确，不能把浏览器刷新误当成第二次发送；网络失败仍保留原填内容并在字段附近说明。
- 验收看什么：正常成功、字段错误、网络失败、重复点击、刷新和390px各两轮；检查焦点、读屏、无大空白和按钮不溢出。

**FB-0905-22｜Landing/Pricing 缺主题和语言控制**

- 问题：未登录的 Landing、Pricing、Contact 没有与工作台一致的主题和语言切换，用户跨页面体验断裂。

**FB-0905-23｜登录后回到未登录页面/Google 链接失败**

- 问题：用户从带目标页的登录入口完成邮箱密码登录后，可能回到 Landing 或 Pricing 的未登录入口；Google 入口也曾失败。

- 准备怎么改：建立会话后再跳转，并在目标页核对登录状态；已登录用户访问登录页时直接前往安全目标。
- 业务边界：拒绝外部网址、伪装斜杠、异常编码和嵌套回跳；一次性授权信息在回调完成后清理，不留在页面地址、截图或记录中。

### C. 发布、排期、历史记录和批量操作

**FB-0905-25｜同一内容同时显示 Posted 和失败**

- 问题：历史 `Publish failures` 中可能出现主徽标为 `Posted`，下方却显示发布失败或待处理，状态自相矛盾。
- 用户影响：用户会误判内容已全部上线，漏掉失败目标；也可能错误重发已经成功的目标。
- 准备怎么改：把“历史曾成功发布”和“当前这次尝试的状态”分开显示；每次尝试只有发布成功、部分成功、失败或结果未知中的一个主状态。
- 准备怎么改：部分成功必须列出每个目标的结果并标为需要关注；失败列表只收录当前仍需处理的尝试。
- 业务边界：成功目标的历史凭证永久保留，新失败不会擦掉它；重试不能改写成功目标，也不能重复发送成功腿。
- 验收看什么：全成功、全失败、部分成功、未知、失败后成功及“历史成功后新失败”各两轮；卡片、Plan、History、筛选和数量必须一致。

**FB-0905-26｜Retry 后没有发布目标的死路**

- 问题：失败卡点击 Retry 后若没有目标，只看到红字和禁用按钮，用户无法在原流程中补选账号或 Board。
- 用户影响：用户知道问题却无法修复，只能退出再四处寻找设置，造成放弃发布或误操作。
- 准备怎么改：Retry先解释为什么无可用目标，分别定位目标未保存、Board缺失或删除、账号断连、权限/能力失效、读取失败。对应字段标红并配文字和修复按钮，自动定位首个错误；不能只显示“0个目标”。
- 准备怎么改：保留原失败原因、内容和目标上下文；支持就地选择Board、重连账号或重试读取。修复后清除对应字段错误，回到同一发布流程；当前已确认意图才可提交，修复不重放历史成功目标。
- 业务边界：缺失、删除、断连、归属不符和能力失效分别说明原因；在嵌套目标编辑中明确点击保存可独立保留该目标编辑，但取消或关闭发布确认本身不得发布、排期、扣额度或调用第三方。
- 验收看什么：逐种制造缺失、删除、断连、归属错误、能力失效及读取失败，确认字段位置、红色边界、文字、首错焦点与修复入口一致；修复后原位恢复。0有效目标时无provider调用/扣量，读取失败不可误报未保存。

**FB-0905-30｜Pin Ideas 不随商品更新**

**FB-0905-31｜无手选 Reference 时生成失败**

- 准备怎么改：标题、媒体、目标、账号以及当前平台所需 Board/Page 放入主编辑区；Details 只放可选的辅助信息。
- 业务边界：Pinterest在能力要求时才强制 Board；Facebook/Instagram 不强制描述、网址或 Pinterest Board；禁用按钮使用用户动作文案而非“0个目标”。
- 验收看什么：缺目标、缺Pinterest Board、缺Facebook Page、账号断连、多项缺失、修复后提交和取消各两轮；桌面/390只出现一条摘要。

**FB-0905-34｜排期和立即发布规则、主次不一致**

- 问题：历史页面出现 Sandbox Board 名称且未证明是用户明确选择；立即发布被高亮，但用户的日常主任务其实是排期。
- 用户影响：用户可能把内容送到默认或过期目标，也可能误以为排期已等于第三方发布成功。
- 准备怎么改：排期保存与立即发布使用同一套目标身份和可用性规则；排期时冻结用户已确认的内容、目标和时间，到期时再核验连接与目标可用性。
- 准备怎么改：排期保存后显示 Scheduled，仅表示VibePin已保存；到期后再显示派发中、已发布、部分成功、失败或未知。
- 业务边界：测试 Board 只要是用户明确选择、归属正确且可用即可；禁止隐藏默认目标和跨账号回退。Schedule保存前不生成公开副本或第三方访问地址。
- 验收看什么：同草稿排期/立即发布对照、无Board、明确测试Board、隐藏回退、断连、部分成功、未知、到期状态和键盘Enter各两轮。

**FB-0905-35｜Batch Edit 输入态不明显**

- 问题：可编辑单元格像普通文字，整行浅紫让用户难以识别真正可输入区域和当前选择状态。
- 用户影响：运营人员会漏填关键内容，或误把只读历史凭证改成当前可编辑配置。
- 准备怎么改：按UI设计审查统一字段结构：常驻标签、明显输入边界、示例、可见focus、脏状态和字段级错误。标题/描述/URL/替代文字/商品/目标/Board/时间逐项定义编辑、保存中、失败和只读状态。
- 准备怎么改：选中用复选框和细边框表达，不整行铺紫。目标字段先选账号再选Board/Page；历史发布回执单独只读展示。保存失败保留输入，保存成功必须可信读回。
- 业务边界：移动端改为纵向编辑器，不将宽表格压缩到不可读；横向表格需保留内容列和选择列的可见性。
- 验收看什么：键盘、鼠标、触控、横向滚动、只读已发布行、390px和批量取消各两轮，确认输入、只读和选中三种状态不混淆。

**FB-0905-36｜Posted 的目标信息与当前编辑状态混淆**

- 问题：用户发现部分已发布Pin没有Board，需要区分历史未记录、同步遗漏、接口未返回、前端未展示与当前目标被清空，不能直接假定只是显示问题。
- 用户影响：商家可能错误重发、删除正确内容，或无法向客户解释历史发布证据。
- 准备怎么改：核对发布请求、远端回执、本地持久化和页面投影四层，查明Board在哪一层丢失。成功时保存平台、账号、Board/Page身份快照、remote id/permalink、postedAt及attempt关联。
- 准备怎么改：如果当前目标被删或账号断连，只影响未来重试/再发布能力，不降低历史成功状态。
- 业务边界：历史缺项标记“历史目标信息缺失，待核对”，保留已有可信成功证据；只能用同一次发布的可信证据补齐。禁止从当前编辑Board或默认Board猜补，禁止为补记录再次发布。
- 验收看什么：单目标/双目标已发、部分成功、未知、目标删除、断连、再发布和历史详情各两轮，确认历史证据始终保留。

**FB-0905-37｜批量混合账号无法正确选 Board**

- 问题：混合账号批量编辑时，每行重复长说明，Board无法设置，`Publish to` 也不能清楚选择哪个账号。
- 用户影响：用户难以批量修复内容，可能把一个账号的 Board 错用到另一个账号，造成错发。
- 准备怎么改：工具条集中显示一次简短 `Mixed accounts` 状态；先选择账号，再只显示属于该账号的 Board/Page。
- 准备怎么改：支持只编辑同账号行、逐行修复，或明确覆盖全部尚未发布行到一个新账号；账号改变立即清除不兼容 Board。
- 业务边界：已发布或结果未知的目标不可被批量覆盖；长说明不应在每行重复，用户必须能看清本次影响范围。
- 验收看什么：同账号、两个Pinterest账号、Pinterest+Facebook、混合Board、账号切换、逐行修复、全量覆盖、取消和390px各两轮。

**FB-0905-39｜Plan 的批量 Publish 名称与实际动作不一致**

- 问题：Plan 中 `Publish selected` 目前实际可能只是进入批量编辑，且选择集合没有证明会被完整处理。
- 用户影响：用户以为已经发布，实际只是编辑；若未来真发布又只处理其中一条，可能造成漏发或错发。
- 准备怎么改：保留Publish selected。点击后按完整已选集合逐条提交真实发布任务，显示“发布已提交，可查看发布结果”及查看结果入口；不得改名为Edit selected，也不得跳进普通编辑流程。
- 准备怎么改：冻结每条内容和目标的提交快照，逐条/逐目标记录已提交、需修复、已跳过、处理中及终态。提交成功只指服务端已可靠接收，Posted必须等第三方成功回执；部分未提交必须同时显示数量和原因。
- 业务边界：发布操作本身须清楚展示范围及精确目标；若需补充确认，使用发布确认而非编辑。提交前取消不派发；提交后关闭面板不中断已接收任务。重复点击不重复发布，已成功/未知目标不盲目重发。
- 验收看什么：1/2/5条、已发布/失败/草稿混选、有效/无目标混选、重复点击、超时恢复各两轮；选择数必须等于可追溯结果数。

**FB-0905-46｜Plan 按钮夸大为 Publish**

- 问题：这是FB-0905-39在文案层的直接风险：按钮写“Publish selected”，实际进入编辑面板。
- 用户影响：用户的心理预期与系统行为不同，尤其在外部发布场景会损害信任并增加客服解释成本。
- 准备怎么改：Publish selected与Edit selected各自保留独立动作。前者提交所选内容发布，后者仅修改内容；修复handler和任务链路，不通过改发布按钮名称规避需求。
- 准备怎么改：服务端可靠接收后提示“发布已提交”，用户可离开并在Plan/History查看逐条结果；尚未接收、部分拒绝或未知时显示真实状态，不能提前提示发布成功。
- 业务边界：完整选择集合逐条有记录，失败行定位字段错误；提交后继续跟踪任务，历史成功不可覆盖。此规则由业务批注明确冻结，后续不得恢复“先改为编辑”的旧方案。
- 验收看什么：桌面/390、鼠标、键盘、无选择、混合选择和页面刷新各两轮，确认名称、实际动作和帮助提示完全一致。

### D. Product、全局界面、可访问性和可靠性

**FB-0905-27｜所有页面去掉独立大标题**

- 问题：页面级大标题挤占首屏。用户要求所有页面都不显示大标题，原先只限制工作台且豁免Landing的规则已被覆盖。
- 用户影响：用户需要滚动才能看到筛选、商品或待办，工作台显得像宣传页而不是运营工具。
- 准备怎么改：移除所有页面独立的大标题/Hero标题占位；工作台首屏直接呈现工具条、内容和状态，公共页、认证页、设置与后台也逐页检查。
- 准备怎么改：页面身份由紧凑导航、面包屑或必要的小型上下文标签表达；保留可访问页面名称与语义h1，可采用视觉隐藏h1。正文必要章节标题、字段标签和法律正文不删除。
- 业务边界：不能用缩到32px替代去掉大标题，也不保留Landing大标题豁免；不影响文档标题、SEO页面title和辅助技术阅读顺序。
- 验收看什么：按完整页面清单，在1440/1280/390及桌面100%缩放各两轮检查无独立大标题和大块空白；导航能辨认页面，键盘和读屏仍有完整页面语义。

**FB-0905-28｜Product 空态不诚实**

- 问题：Digital 筛选显示“没有匹配商品”时，无法区分真筛选空集、商品库为空、仍在加载还是同步/权限错误。
- 用户影响：商家会做出错误商业判断，把数据故障当成没有商品机会，或因假空态停止排查连接问题。
- 准备怎么改：分开显示筛选为空、全库为空、加载/刷新、权限不足、服务错误和过期缓存；每种状态给出相应下一步。
- 准备怎么改：商品数量、可筛选项和已保存商品从同一可信结果读取；过期数据可暂时展示，但必须标明正在刷新。
- 业务边界：不插入演示数据冒充恢复；错误不会被吞成空数组，重试只更新当前查询并保留用户筛选。
- 验收看什么：有商品但Digital=0、全库=0、加载、过期、401、403、限流、服务错误、超时和重试成功各两轮。

**FB-0905-29｜Product 类型筛选位置突兀**

- 问题：All products/Physical/Digital 悬在标题和筛选条之间，用户难以理解它是否与搜索、分类和排序同属一组条件。
- 用户影响：筛选心智负担增加，390px下更容易挤压结果区或出现横向滚动。
- 准备怎么改：把 Product type 纳入统一筛选工具条，明确标签，与搜索、Category、Platform、Sort 共享应用和清除规则。
- 准备怎么改：要么选择即生效，要么全部点击 Apply 后生效，只保留一种模型；未提交状态必须可见。
- 业务边界：安全且可分享的筛选才可恢复到链接；私有选择、未保存输入和操作意图不能写进地址。
- 验收看什么：三种类型与其他筛选组合、Apply/Clear、刷新、Back/Forward、键盘和390px各两轮，无布局跳动。

**FB-0905-38｜全局 UI 有模板感且交互不连续**

- 问题：巨型标题、粉紫大按钮、大色块、胶囊堆叠、卡片套卡片、长解释和跳变动效，使产品像通用AI模板而非可靠运营工具。
- 用户影响：内容、状态和下一步被装饰抢走注意力；用户在快速操作时容易错过等待、失败或焦点位置变化。
- 准备怎么改：采用安静、内容优先的工作台视觉：中性表面、清晰文字层级、细分隔、有限圆角，品牌色只服务当前选择、焦点和唯一主要动作。
- 准备怎么改：点击100ms内有反馈；慢操作显示局部进度；动效只帮助理解开关和位置变化，随时可中断并尊重减少动效偏好。
- 业务边界：视觉“丝滑”不允许假成功、盲重试或提前显示发布完成；悬停不是唯一功能，键盘、触控和390px要有等价路径。
- 验收看什么：建立桌面与390px对比截图；关键“选内容→补字段→选目标→排期”两轮计时，记录反馈、布局位移、焦点、滚动和重复提示。

**FB-0905-40｜控件、键盘与模态基础不统一**

- 问题：部分点击区域不是原生控件，字段标签关联、关闭按钮名称、焦点圈闭、焦点归还和背景滚动规则不统一。
- 用户影响：纯键盘、读屏、移动端和行动不便用户可能无法选择素材、关闭抽屉、提交表单或返回原位置；这是核心可用性阻断。
- 准备怎么改：优先使用真实按钮、链接和输入框；自定义控件必须具备完整键盘操作、可访问名称和清晰选中状态。
- 准备怎么改：所有弹窗/抽屉打开时保存触发点，Tab留在内部，Escape/关闭后回到触发点，背景不可误操作，页面只保留一个滚动归属。
- 业务边界：表单错误保留已填内容，在字段旁提示并将焦点移到摘要或第一个错误；固定底栏不能遮住最后一个字段。
- 验收看什么：只用键盘完成登录、Contact、Reference选择、Batch Edit、设置和发布确认；桌面/390各两轮并做基础读屏顺序检查。

**FB-0905-41｜图片、长列表与页面跳动风险**

- 问题：多个区域直接一次性展示大量图片或记录，图片尺寸、骨架屏和失败状态未形成统一策略。
- 用户影响：60条以上数据会卡顿，图片慢到或失败会推挤按钮和文字，用户可能误点或丢失滚动位置。
- 准备怎么改：超过50条使用分页、逐步加载或窗口化；图片请求前保留比例和位置，首屏与非首屏采用不同加载优先级。
- 准备怎么改：搜索、筛选、刷新只更新受影响项，保留滚动锚点和已选项；单项失败可单项重试，不重置整页。
- 业务边界：不能凭静态代码就声称已经发生页面跳动或已经通过；必须以实际慢图、错误图和长列表观察结果判定。
- 验收看什么：28、60、120、500条，慢图、404、无法解码、10秒超时、滚动中筛选/刷新各两轮，记录布局位移和交互延迟。

**FB-0905-42｜可分享状态与私有状态边界不清**

- 问题：筛选、详情、语言、主题、草稿、选择和未保存输入在刷新与Back后恢复规则不统一，存在把私有内容带入链接的风险。
- 用户影响：用户体验上会丢上下文；安全上可能把草稿、任务、目标或授权信息暴露给复制链接的人。
- 准备怎么改：只允许明确批准的公开筛选、排序、视图、分页和公开资源标识进入链接；现有受权限保护的 opaque 详情路径可继续保留，每个页面定义默认值、长度和规范格式。
- 准备怎么改：禁止把草稿、选择集合、用户/工作区、发布目标、未保存标题和描述、令牌、付款会话、私有图片地址或任何操作参数新增进可分享链接；这些状态留在安全会话或用户范围内。
- 业务边界：刷新后不能安全恢复的状态，要诚实说明并回到安全页面；Back/Forward只能恢复界面，不得重放生成、发布、排期、付款或授权。
- 验收看什么：刷新、复制链接、新标签、Back/Forward、登录前后、超长/异常/重复参数、简体中文/繁体中文/英文及全部已支持语言和三种主题各两轮，检查地址和截图无私密字段。

**FB-0905-43｜公共页与账户流程的异步反馈不一致**

- 问题：Auth、Pricing、Contact、Settings/Social 的加载、错误、恢复和确认方式各不相同，用户需猜每页该怎么做。
- 用户影响：用户可能重复提交、错过字段错误或因为弹窗过多而放弃，客服也难以给统一指引。
- 准备怎么改：统一空闲、校验、提交中、成功、失败和可重试状态；字段错误就地显示，页面级提示只承担摘要。
- 准备怎么改：良性动作如筛选、打开详情、保存可撤销偏好不强制二次确认；只有外部副作用、不可逆覆盖或可能丢失未保存内容才确认。
- 业务边界：Google、付款、社交账号连接和设置保存各自保留真实回读，不能因统一样式而统一成假成功或全局转圈。
- 验收看什么：登录、注册、重置密码、价格切换、Contact、设置脏状态、社交目标加载失败和移动端各两轮，确认恢复动作一致。

**FB-0905-44｜旧根级页面形成第二套流程**

- 问题：旧 Dashboard、Settings、Preview 仍可能可达，形成与新工作台并行的写入或发布入口。
- 用户影响：用户从旧书签进入时可能看到不同数据、不同安全规则，甚至绕过最新确认与归属保护。
- 准备怎么改：旧入口退役或安全跳转到唯一工作台入口；历史分享若确有需要，只保留可撤销、只读、权限正确的独立分享方式。
- 准备怎么改：每条旧地址逐一规定跳转目标、哪些安全筛选可带过去、哪些私有或动作参数必须丢弃，不能笼统透传。
- 业务边界：未经实测不能宣称旧页已越权；一旦发现旧页错写、越权或绕过发布门禁，立即按P0处理。旧页面不得继续调用旧写入流程。
- 验收看什么：登录/未登录、旧书签、刷新、Back/Forward、无效参数和异常私有参数各两轮，确认三类旧入口均无第二套设置或发布界面。

**FB-0905-45｜设置保存失败却显示成功**

- 问题：旧设置页在网络保存失败时可能仍提示“已保存”，没有证明本地或服务端真的持久化。
- 用户影响：用户以为语言、通知或账号配置已生效，实际下次打开又丢失，尤其会误导发布相关设置。
- 准备怎么改：只有可信的本地持久化或服务端回读成功后才显示成功；否则保留未保存状态与短错误，并给重试入口。
- 准备怎么改：若正式支持离线保存，必须明确“待同步”、归属、版本和后续回读；不支持则不把网络失败包装成离线成功。
- 业务边界：旧设置入口退役后仍要保留回归检查，防止同类假成功迁入新设置弹窗；A→B→A不让旧响应覆盖新值。
- 验收看什么：200、400、401、冲突、限流、500、断网、响应丢失、A→B→A各两轮；成功、待同步和失败必须一眼可区分。

**FB-0905-47｜公共/Auth/法务缺统一可访问外壳**

- 问题：公共、登录和法务页面的主要内容区、跳过导航、焦点、语言和主题表现不一致，首屏也可能闪烁。
- 用户影响：键盘用户需要重复绕过导航；多语言用户先看到错误语言或主题，降低基本可信度。
- 准备怎么改：统一公共外壳和法务布局，提供唯一主要内容区、跳过导航、标题锚点、可见焦点、移动导航及一致页脚。
- 准备怎么改：语言方向和主题在首屏就正确应用；页面异常和无脚本情况下仍提供安全返回和恢复路径。
- 业务边界：公共壳层不替代登录权限判断；无论视觉统一与否，私有内容、授权回调和客户数据仍由各自安全规则保护。
- 验收看什么：Landing、信息页、法务、登录注册在桌面/390各两轮，检查Tab路径、跳过导航、翻译、主题、异常返回和无横向溢出。

**FB-0905-48｜跨页状态一致性与性能不足**

- 问题：筛选、详情、History、Plan、Studio 的同一记录可能使用不同状态来源，长列表也可能影响恢复与性能。
- 用户影响：用户看到 History 已有记录而 Plan 为空，或刷新、返回后丢筛选和滚动，无法相信任务是否真的完成。
- 准备怎么改：对可分享的筛选建立统一恢复规则；对私有选择保留用户范围内状态；同一发布生命周期在 Studio、Plan、History、Queue 中使用同一事实。
- 准备怎么改：长列表、图片、加载、空态、部分成功和未知状态按统一质量门槛处理，避免一个页面“已发”另一个页面“失败”。
- 业务边界：恢复界面状态不得重放任何外部动作；旧页面或局部缓存不能覆盖刚确认的真实结果。
- 验收看什么：刷新、新标签、Back/Forward、浏览器恢复、登录前后、28/60/120/500条、慢图和390px各两轮，核对同一记录跨页一致。

**FB-0905-49｜Settings/Admin 基础交互不统一**

- 问题：设置与管理后台存在空白深链、双重呈现、原生确认框、表格焦点和权限导航不一致等风险。
- 用户影响：管理员和普通用户可能在错误页面迷失、看见无权入口、无法用键盘处理表格，或在危险动作前没有适当确认。
- 准备怎么改：建立一致的弹窗/抽屉、确认、字段、异步状态、表格、图片和日期时间使用规则；深链必须有明确页面或可恢复跳转。
- 准备怎么改：后台按角色呈现可用导航；不可逆终态动作需要确认或短期撤销，普通筛选和浏览不加无意义确认。
- 业务边界：设置可用弹窗架构不等于可以空白；智能排期只能保留一种呈现和一种滚动归属，避免页面与弹窗重复。
- 验收看什么：11类设置页签与13条路由规则、管理表格键盘操作、权限不足、保存失败、危险操作确认、长表和390px各两轮。

**FB-0905-50｜授权回调遇异常 next 可能中断**

- 问题：回调读取异常编码的 `next` 时可能在保护逻辑前中断，导致500或无法回到安全页面。
- 用户影响：正常用户遇到坏链接、旧cookie或浏览器恢复时可能无法登录；若处理不当还可能形成外部跳转风险。
- 准备怎么改：所有回跳来源共用“不抛异常”的清理规则：先限制长度并安全读取，再拒绝外部地址、伪装斜杠、反斜杠、控制字符、嵌套和双重编码。
- 准备怎么改：明确定义页面参数与cookie谁优先；任何异常回到固定站内页面，成功、失败、重复回调和返回操作后清理一次性信息。
- 业务边界：当前登记的是可靠性与输入验证缺口，未经实测不得断言已存在开放跳转或绕过；若证实则立即升为P0。
- 验收看什么：合法目标、缺失目标、畸形%、单双编码外部地址、超长、重复键、cookie冲突与回调重放各两轮；不得500、循环、外跳或泄露。

## 四、跨文档必须一起落地的六项业务裁决

**U24-01｜草稿图片隐私与发布副本分离**

- 草稿、上传图、生成中间图和未发布成品默认只让对应用户查看，不能因“方便第三方读取”而长期公开整类素材。
- 真正点击并确认发布后，才为该次发布、该个目标准备单独可追溯的交付副本；确认前、未派发和取消均不新增公开副本。已实际派发后若失败或结果未知，副本按有限时效保留以便核对与恢复，再按清理规则处理，不承诺不安全的即时删除。
- 商家看到的是安全预览，不是原始私有地址；第三方所需资源与草稿资源分开，历史发布证据仍可保留。
- 验收：匿名不能读草稿、本人可读、跨用户不可读；确认前无公开副本，取消/失败无新增公开副本，成功副本可追到本次发布和目标。

**U24-02｜历史公开图片迁移与归属不明隔离**

- 先盘点历史公开图片和既有依赖，再迁移；不能为了关闭告警直接删除历史内容或一刀切改变可见性。
- 能高置信匹配到用户和来源的历史图，逐步纳入私有读取与可追溯管理；归属冲突或无法确认的对象进入隔离状态，不继续公开、不冒领给任何用户。
- 迁移观察期保留兼容读取与核验，确认无误后才关闭旧公开读取；回退只调整读取策略，不重新把所有私有素材公开。
- 验收：逐项核对归属、内容一致性、本人读取、跨用户拒绝、归属不明隔离和旧新读取切换，形成可审计但不泄露私密链接的报告。

**U24-03｜生成数量必须完整兑现，后台容量不能静默截断**

- 用户请求的总图片数固定为：`max(参考图数, 1) × 每张参考图的变体数`；产品数决定每张图中出现几个主体，不参与张数相乘。
- 例：3个产品、2张参考图、每张参考图4个变体，应交付8张图；每张图中是3个产品同框。没有参考图时仍可生成，至少按1组计算。
- AI图片额度按实际成功图片张数结算：失败不结算，结果未知先核对再处理；不要误写为“一次意图只扣一次”。跨平台发布的同一内容另有其自身计量规则，不能混淆。
- 第三方单次处理容量只影响后台如何分批，不得静默减少用户请求数量；不另按套餐臆造图片数量硬上限。业务承诺完整交付、可见进度、坏项单独恢复，不承诺无限并发。
- 验收：无参考、单/多参考、多产品、部分失败、全失败、未知、分批完成与重试各两轮，核对请求张数、成功张数、剩余待处理数和额度完全一致。

**U24-04｜草稿单条同步，切账号不串草稿**

- 草稿同步遇到坏项时，坏项应明确标出并可单独恢复，不能拖累同一用户其他好草稿，更不能让全页显示为失败。
- 所有草稿、选择、参考、上传与生成准备信息必须按用户和工作区隔离；切换账号、刷新、A→B→A不能露出或保存另一账号的草稿。
- 网络响应较晚时，以用户最后一次选择为准；新草稿和旧草稿的图片、标题、目标和状态不能互相覆盖。
- 验收：好坏草稿混合、断网重连、单项失败重试、快速切账号、切工作区、刷新和返回各两轮，检查好项连续可用、坏项可见、零串数据。

**U24-05｜实施版本分歧先确认，旧测试不能证明新环境完成**

- 每次进入实施或验收前先确认唯一候选版本和唯一测试环境；不同分支、历史部署、旧截图只能作为参考，不能拼成今天的通过结论。
- 修复要在同一最终环境重新走关键流程，并把“静态发现、历史用户报告、当前实机结果”分开记录。
- 出现版本不一致时，先停止宣称完成，核对当前页面、行为和关键回读后再继续；不因某个旧测试全绿就跳过新环境验证。
- 验收：每个P0在最终候选环境给出两轮实际操作和截图；报告清楚标注未执行、失败、部分完成，不把历史PASS迁移为当天PASS。

**U24-06｜真实链路验收与副作用边界**

- 发布、排期、付款、生成、上传、账号连接和额度都属于可能改变外部状态的动作，验收必须明确哪一步只是打开页面、哪一步会真正产生副作用。
- 取消、Escape、关闭、打开选择器、浏览和筛选默认不产生发布、扣费、第三方调用或公开副本；用户明确保存独立设置时只保存该设置，仍需重新确认高风险动作。
- 真实链路验收要看最终页面、实际状态回读、逐目标结果和失败恢复，而非仅看按钮可点或历史自动化通过。
- 验收：为每类动作记录开始前、确认边界、取消后、成功、失败、未知和恢复后的实际状态；对安全拦截场景证明没有外部调用或额度变化。

## 六、最终验收怎么做

### 1. 两轮原则与视口

每个关键流程必须在同一最终测试环境完成两轮独立操作；每一轮都同时覆盖正常路径和相应异常/恢复路径。第二轮额外使用新会话，重点验证刷新、缓存、返回、账号切换和重复点击不会把第一轮结果误当成当前结果。桌面至少覆盖1440/1280及关键窄桌面；移动以390×844为准。390px下不得横向溢出、双重纵向滚动或固定底栏遮挡字段，点击目标至少应便于触控。

### 2. 四套餐截图报告

Free、Starter、Pro、Business使用四个彼此隔离的合成账号，各两轮。报告对每轮保存脱敏的默认、接近上限、达到上限、失败/未知状态截图，并记录套餐展示、实际已成功使用量、暂时占用、是否拦截、失败是否释放、切账号是否隔离。不得通过大量真实生成消耗额度；当前模式若只是观察而未拦截，要如实单列，不冒充产品失败或通过。

### 3. 错误截图与恢复报告

对生成、商品加载、登录、付款、目标选择、排期、发布、设置保存和图片读取，统一记录：用户做了什么、页面告诉用户什么、下一步能否完成、取消后是否零副作用、最终状态是否与历史/列表一致。截图只放安全文案和状态，不放密码、验证码、令牌、私有媒体地址、账号标识或付款资料。

### 4. 发布与排期的真实边界

打开确认页、选择器、抽屉或普通编辑不等于发布。只有用户看见精确内容、平台、账号、Board/Page、时间和影响范围并确认后，才允许进入实际动作。排期保存后必须可在卡片和历史中读回；到期执行再单独确认目标能力与第三方结果。成功、部分成功、失败和未知都必须可解释、可恢复、不可互相伪装。

### 5. 放行标准

- 所有P0在同一最终环境有两轮实际证据；历史记录和旧分支测试不能替代。
- P1要么关闭，要么由业务负责人书面接受延期及替代办法。
- 四套餐证据以 `docs/审查报告/0906-四套餐Credit测试执行报告-zcode.md` 为唯一汇总入口；报告含脱敏截图与四套餐×两轮×用例分列结果。登录、付款测试、生成、私有媒体、发布/排期、跨账号隔离和64页业务族都留下明确结果；报告尚未创建或相关项为NOT_EXECUTED时不得放行。
- 没有未授权的真实付款、正式环境修改、公开素材放开或第三方发布。
- 最终报告允许写“未执行”“部分完成”“失败”；不允许用“文档已完成”替代产品完成。

## 七、当前决策摘要

本轮最大的业务风险集中在：内容是否属于正确用户、生成数量和额度是否诚实、发布是否发往用户明确选择的目标、排期是否被误认作已发布、以及历史成功是否会被新失败覆盖。先完成这些事实链路，再统一页面风格，才能把 VibePin 做成可信的 Pinterest 内容运营工具。

截至本版本：本批需求汇总完成，但尚未全部实现；历史环境已有的部分只读界面观察和代码测试证据不因本轮整理而失效，也不等同于当前最终环境的两轮通过。当前最终环境的完整两轮验收、四套餐证据和真实第三方链路验证仍待完成。正式环境放行结论仍为：**不放行**。

### 发布提交与结果的业务闭环

Publish selected必须保留完整选择集合，逐条记录已接收、需修复、已跳过或未接收。全部接收时显示“已提交N条发布，可查看结果”；部分接收同时显示需修复和跳过数量。只有服务端已可靠保存，才能说“发布已提交”；只有第三方成功回执才能说Posted。用户关闭提交面板后仍可在Plan/History查结果，不能因此取消已接收任务。

已发布却没有Board时，核对原发布请求、第三方回执、保存记录和页面显示。缺失历史信息明确显示“历史目标信息缺失，待核对”，不能拿当前Board猜补，也不能通过再发一次补记录。当前目标断连不抹除可信历史成功。

### 推荐和生成的当前可用性

当前代码有商品相关参考接口，也有读取trend_keywords和pin_samples的机会推荐，但路径没有完全统一。一个推荐选择路径只把风格标签送进提示词，不把推荐图片本身当style reference；界面不能把这两种使用方式都叫“已选参考图”。旧图片选择器及通用图库也不能冒充已按当前商品推荐。

本轮三组本地测试通过：参考评分13项、创意推荐12项、生成manifest48项，共73项。这证明相应本地规则通过，不证明当前数据库有合格候选、线上模型可用或两张生成失败已修好。自动推荐应标记为“部分链路存在，完整商品图+趋势+数据库+生成链路未完成实机验证”。用户要求的线上失败根因仍需要同一次请求的错误阶段、状态码和支持编号，不能用候选原因替代。

## 十 UI会话确认后的视觉与交互合同

本节落实C01和C13的两条新增批注。方案来自Codex「UI」任务的只读审查，结论为建议采纳。这里写的是目标合同，不代表当前实现已完成；现有截图只覆盖部分登录后路由和部分尺寸，不能据此关闭全站验收。

### 1. 四个业务验收视口

| 视口 | 页面容器和列 | 关键规则 |
|---|---|---|
| 1440×900 | App rail 68px；工具/数据页最大1280px并居中；左右32px；媒体4列仅在单卡不低于260px时使用；编辑卡3列且单卡不低于320px；gap 16px | 首屏至少完整显示第一行；不能缩字号、热区或按钮来维持列数 |
| 1280×800 | rail 60–68px；左右24px；媒体3列且单卡不低于280px；编辑卡字段或动作不足320px时降2列 | 不得硬塞3列导致字段、按钮或状态变形 |
| 1007×632 | rail 60px或可关闭drawer；左右24px；主内容2列且每列不低于320px | Studio详情、Plan未排期区和长筛选使用drawer/overlay；Weekly Plan默认day/list；页面只有一个纵向滚动owner |
| 390×844 | 无侧rail；顶部品牌栏56px、底部主导航；左右16px；单列358px内容宽；区块间距16px | 筛选为摘要按钮加sheet；主动作和Retry常驻；触控热区优先44×44px且不小于40×40px |

正文、表单和卡片动作不得产生页面级横向滚动。确需横向比较的数据区只能局部滚动，并给出边缘渐隐或“横向滚动查看更多”提示。drawer/modal自行滚动；关闭后恢复原页面滚动和触发点焦点。1024/768只作为工程插值检查，不能替代1280/1007业务验收。

### 2. 首屏和卡片稳定性

- 顶栏下不放独立标题带或Hero空白；紧凑上下文/筛选条建议40–48px高，首个可操作内容在顶栏下72–128px内出现。
- 1440/1280媒体列表首屏至少出现完整第一行；1007至少完整显示2张核心卡；390至少完整显示1张卡并露出下一项或后续状态，创建表单和法务正文除外。
- 媒体槽预先锁定比例；loading、success、failed、image unavailable和retry不能改变卡片外框高度。状态摘要最多两行，动作区单独一行；桌面控件至少36px，移动热区至少44px；长诊断放进展开详情。
- 旧视觉回归单独验收：失败卡不得出现粉/紫大色墙、破图、原始文件名或永久spinner。这一项不得与数据stale混为同一结论。

### 3. stale业务规则

stale只表示页面仍显示最后一次可信成功快照，但freshness TTL已过、请求版本落后于当前筛选/商品/账号版本，或刷新失败后保留旧快照。没有可信快照必须进入error/unavailable；用户觉得内容旧或界面样式旧，不能自动判为数据stale。

- 视觉保留真实快照，不整卡染黄/红；在数据摘要或元数据位置显示低饱和warning图标、更新时间和1px warning边界/左rail，颜色不是唯一信号。
- 更新中文案：`正在更新 · 当前显示 {time} 保存的数据`；更新失败：`未能更新 · 当前显示 {time} 保存的数据`；详情说明：`部分信息可能已变化，更新前不会自动覆盖你的编辑。`
- 默认动作是`刷新数据`，失败后同位改为`重试刷新`。刷新本身不能生成图片、扣生成额度、排期或发布。
- stale数据将用于生成、排期或发布时，主动作前必须由服务端preflight/readback。发现版本或目标冲突时显示`查看最新变化`，禁止静默覆盖或携带旧目标继续提交。
- loading使用同尺寸skeleton；empty只在权威成功且集合为0时出现；filtered-empty提供Clear filters；partial保留成功内容并提供`重试未完成部分`；unknown不报成功并提供`检查状态`。
- 状态live region只播报一次；pending按钮保持宽度；Tab顺序按视觉顺序；2px focus-visible不被裁切；Escape只关闭最上层overlay。

### 4. 删除所有独立大标题后的页面结构

- App工具页删除“PageHeader大标题 + 描述 + 大段上边距”。页面身份放进app topbar的14–16px route label，必要时加breadcrumb；main保留唯一sr-only h1，路由切换后焦点进入main或h1。
- Studio的topbar显示Studio/Create Pins，main直接进入Creation Rail；列表和分析页从FilterBar、scope controls或result summary开始；Settings route使用sr-only h1，modal/drawer可有18–20px且通过aria-labelledby关联的对话框标题。
- Help和法务文章不放独立banner，但文章名是必要正文层级，可在阅读列保留24/30 h1并紧接目录或正文；不得使用36–60px Hero、渐变标题或额外空白带。
- Admin页名进入admin topbar/breadcrumb，内容从状态摘要或表格开始；Auth只在表单卡内保留20–24px任务标题，页面外不重复。
- Landing撤销豁免。导航下直接进入可操作演示或证据组件；价值主张改为与演示同组的18–24px简短intro，不保留48–64px Hero或只为标题服务的大空白。保留唯一sr-only h1且与可见首屏语义一致；业务h2与真实内容同组，桌面建议不超过32px。

每个route仍必须有准确唯一的document title、description、canonical（适用时）和OG metadata。隐藏h1、document title和可见route label语义一致；不得删除h1后从h2开始，也不得放多个sr-only h1。breadcrumb使用nav、aria-label和aria-current；sr-only h1使用统一类，不能用display:none或hidden。

### 5. 按钮、冲突替换和验收

- 创建/生成使用`Create Pin`或`Generate Pins`；排期使用`Schedule`；立即发布使用次级`Publish now`；筛选使用`Filters`、`Apply filters`、`Clear filters`；stale使用`Refresh data`、`Retry refresh`；错误使用`Retry`；冲突使用`Review latest changes`。
- 同一surface只有一个primary。按钮使用动词加对象；pending可改进行态但宽度不跳；禁用原因在邻近位置解释，不能用`0 targets`等状态量代替动作名。
- 旧设计规范中“页面顶部统一PageHeader”和“PageHeader → …”配方作废，替换为：每页唯一语义h1；工具页默认sr-only，页面身份由紧凑topbar/breadcrumb承担；仅文章/表单中属于正文结构的h1可见；禁止独立PageHeader/Hero占位。
- 当前Landing/公共/法务的3xl–6xl标题、Landing `transition:all`、Insights 26–36px标题等冲突登记为待实施，不得写已完成。
- 验收按Landing/Public、Auth、App shell、Studio、Plan、History、Discover/Trends/Products/Insights、Settings、Help/Legal、Admin逐族执行。每族覆盖四个golden视口、100%缩放和200% zoom；light/dark/system；全部已启用语言和长文案；loading、empty、filtered-empty、success、partial、stale、error、unknown；mouse、keyboard、touch、focus、Escape、scroll restore、reduced motion、44px热区和零页面级横向溢出。
- Round 1使用干净session；Round 2在刷新、Back、重登和A→B数据切换后复走。每格只能写PASS、FAIL或NOT_EXECUTED，不以截图存在替代交互验收。
