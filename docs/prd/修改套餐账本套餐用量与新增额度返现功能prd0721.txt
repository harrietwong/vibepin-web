Implement a complete production-grade credits, usage metering, billing-cache, account-isolation, and referral-reward system for VibePin.

The current problem is that image and text generation succeed without consuming credits, the Credit UI does not show meaningful usage, and the Billing page waits for a slow external subscription request every time it is opened.

This task must fix the backend accounting logic, not only the frontend display.

Do not change existing Creem product prices, checkout links, product IDs, webhook secrets, or subscription mappings unless a verified bug requires it. Preserve the existing moderation flow and ensure rejected prompts never consume credits.

# 1. Inspect the current implementation

Before editing, identify:

* all subscription plans and their existing names
* the source of plan and pricing configuration
* all image-generation endpoints
* all text-generation endpoints
* regeneration, retry, batch, queue, worker, and fallback paths
* existing user, account, subscription, and usage tables
* current Creem webhook handling
* current Billing page data-loading flow
* all places where credits or usage are displayed
* whether the application supports individual accounts only or also supports teams/workspaces

Do not create a second disconnected credit system if one already exists. Migrate or repair the current implementation.

# 2. Establish one source of truth for plan allowances

Every active plan must have an explicit monthly credit allowance.

Use the existing plan identifiers and product mappings. Add a centralized server-side plan-entitlements configuration containing at least:

* internal plan key
* Creem product or price identifier
* display name
* monthly credit allowance
* permitted product features
* optional generation limits
* subscription rank for upgrade comparisons

Example structure:

```ts
type PlanEntitlement = {
  planKey: string;
  displayName: string;
  monthlyCredits: number;
  creemProductIds: string[];
  features: {
    textGeneration: boolean;
    imageGeneration: boolean;
    batchGeneration: boolean;
  };
};
```

Do not hardcode allowance values separately in frontend components, API routes, and webhook handlers.

If current pricing pages already advertise generation allowances, use those values.

If no allowances currently exist, create the configuration structure but clearly report which allowance values require a product decision. Do not silently invent contradictory limits.

# 3. Define generation credit costs centrally

Create one server-side credit-cost configuration.

Recommended initial cost model, unless an existing documented model already exists:

* generate text content: 1 credit per completed request
* rewrite or regenerate text: 1 credit per completed request
* generate one image: 5 credits per completed image
* regenerate one image: 5 credits per completed image
* batch image generation: number of successfully generated images × 5 credits

The cost must be configurable without editing generation handlers.

Example:

```ts
export const CREDIT_COSTS = {
  textGeneration: 1,
  textRewrite: 1,
  imageGeneration: 5,
  imageRegeneration: 5,
} as const;
```

The UI must read the same effective cost configuration through a safe server endpoint or server-rendered data. Do not duplicate the values manually in client code.

# 4. Use a ledger-based credit architecture

Do not implement credits as only one mutable `users.credits` number.

Create or repair a ledger-based design containing the equivalent of:

## Credit account

One credit account per authenticated user or billable workspace.

Suggested fields:

* id
* user_id or workspace_id
* recurring_balance
* bonus_balance
* reserved_balance
* billing_period_start
* billing_period_end
* plan_key
* version
* created_at
* updated_at

## Credit ledger

Every credit change must create an immutable ledger record.

Suggested fields:

* id
* credit_account_id
* user_id or workspace_id
* operation type
* amount
* balance before
* balance after
* credit bucket
* source
* reference type
* reference ID
* idempotency key
* metadata
* created_at

Operation types should include:

* monthly_allocation
* generation_reservation
* generation_charge
* reservation_release
* referral_reward
* promotional_credit
* manual_adjustment
* refund_reversal
* subscription_change
* expiration

Credit buckets:

* recurring monthly credits
* bonus or referral credits

Recurring credits reset or expire according to the subscription billing cycle.

Bonus credits should not disappear during a normal monthly reset unless an explicit expiration date exists.

Spend recurring credits before bonus credits so that credits expiring sooner are used first.

# 5. Deduct credits correctly for every generation

Every image and text generation path must use this order:

1. Authenticate the user.
2. Derive the user or workspace ID on the server.
3. Validate the request.
4. Run prompt moderation where required.
5. Calculate the expected credit cost.
6. Atomically reserve the required credits.
7. Start generation only after the reservation succeeds.
8. On successful generation, settle the reservation as a charge.
9. On failure, timeout, cancellation, or provider error, release the reservation.
10. Return the updated balance to the client.

Do not deduct credits when:

* moderation rejects the prompt
* moderation is unavailable
* request validation fails
* the AI provider is never called
* generation fails
* generation times out
* no usable result is returned
* the user cancels before generation begins

For partial batch success, charge only for successfully completed outputs.

A generation must not start when the available balance is insufficient.

Return a stable error:

```json
{
  "code": "insufficient_credits",
  "message": "You do not have enough credits for this request."
}
```

The UI should show:

`You need {required} credits, but only {available} credits are available.`

Include an upgrade or view-plans action.

# 6. Make all credit operations atomic and idempotent

Use database transactions and row locking or an equivalent concurrency-safe mechanism.

Two simultaneous requests must never spend the same credits.

Every generation request must have a unique server-side idempotency key.

Retries of the same request must not create duplicate charges.

Enforce uniqueness for relevant idempotency keys at the database level.

Do not rely on frontend buttons being disabled as the protection against duplicate charges.

# 7. Monthly credit allocation and reset

Monthly allowances must follow the user’s actual subscription billing period, not simply the first day of the calendar month.

Store:

* current period start
* current period end
* last allocation event
* next reset date

When a paid subscription is activated or renewed:

* update the subscription snapshot
* allocate the plan’s recurring credits exactly once
* record an immutable monthly allocation entry
* update the billing-period dates

When a subscription is upgraded:

* apply one documented proration rule
* do not accidentally allocate the full allowance multiple times

Recommended initial upgrade rule:

* preserve the user’s already consumed amount
* increase the cycle allowance to the new plan allowance
* grant only the positive difference when appropriate

When downgraded:

* schedule the lower allowance for the next billing cycle unless the existing billing implementation already applies immediate downgrades

When canceled:

* retain current-cycle access until the subscription period ends when that matches the current Creem subscription behavior
* do not allocate another recurring allowance after expiration

Webhook retries must not duplicate monthly allocations.

# 9. Improve Billing page loading speed

Do not call Creem synchronously every time the user opens Settings → Billing.

Create a local subscription snapshot table or extend the existing subscription table.

Store at least:

* user or workspace ID
* Creem customer ID
* Creem subscription ID
* plan key
* product ID
* status
* billing interval
* current period start
* current period end
* cancel-at-period-end
* last synchronized timestamp

Update this snapshot primarily through verified Creem webhooks.

The Billing page should:

1. Render the local subscription snapshot immediately.
2. Render the local credit account immediately.
3. Avoid a blocking external Creem request.
4. Optionally trigger a background refresh when the snapshot is stale.
5. Keep showing the last verified snapshot while refreshing.
6. Show a small non-blocking refresh status rather than replacing the page with a spinner.

Use a stale-while-revalidate approach.

Recommended cache behavior:

* recent local snapshot: return immediately
* stale snapshot: return immediately and refresh in the background
* missing snapshot: perform one controlled server-side synchronization
* external API unavailable: continue showing the last verified snapshot with a warning

Do not show the wrong plan while loading.

Do not temporarily show Free when a paid-plan lookup is pending.

# 10. Enforce strict account isolation

All credits, usage, subscriptions, referrals, and billing data must be isolated by authenticated account.

Never accept `userId`, `accountId`, or `workspaceId` from the browser as proof of ownership.

Derive identity from the authenticated server session.

Every query must include the authenticated owner scope.

For workspace-enabled systems, derive the billable workspace through verified membership and role checks.

Add database constraints and row-level security where supported.

A user must never be able to:

* view another user’s balance
* view another user’s usage history
* spend another user’s credits
* access another user’s subscription
* use another user’s referral data
* modify another account through an object ID
* guess IDs to access another account

Administrative access must use an explicit privileged path with audit logging.

Do not mix email-address-based ownership with immutable user IDs.

Account-email changes must not create a new credit account or expose the previous account.

# 11. Add a referral-credit system

Implement credit rewards first. Do not launch cash payouts in this version.

Cashback introduces additional payout, fraud, refund, accounting, and compliance requirements. Keep the architecture extensible for a future affiliate system, but launch referral credits now.

Each eligible user receives:

* a unique referral code
* a shareable referral URL
* referral statistics
* pending rewards
* granted rewards

Example URL:

`https://vibepin.co/?ref=ABC123`

Capture the referral code at first qualified visit and associate it with signup.

Do not overwrite an existing valid referral attribution on every visit.

Create equivalent tables for:

## Referral code

* owner user ID
* code
* active status
* created_at

## Referral relationship

* status
* qualifying event
* reward status

## Referral reward

* source payment or subscription reference
* pending date
* granted date

* reason
* idempotency key

# 12. Referral qualification rules

Recommended initial rule:

A referral becomes qualified only after the referred user:

1. creates a new account through a valid referral link
2. is not the referrer
3. completes the first successful paid subscription payment
4. has not already qualified through another referrer
5. has no refund, cancellation fraud, or chargeback during the configured holding period

Make reward amounts configurable.

Recommended product configuration:

```ts
export const REFERRAL_REWARDS = {
  inviterCredits: 100,
  newUserCredits: 50,
  qualifyingEvent: "first_paid_subscription",
  holdDays: 7,
  maxRewardsPerMonth: 20,
};
```

These are proposed defaults and must remain configurable.

If a first payment is refunded or charged back before the reward is released:

* cancel the pending reward

If credits were already granted and the payment is later reversed:

* create a reversal ledger entry
* never silently edit old ledger entries

Referral webhooks must be idempotent.

# 13. Referral abuse prevention

Block or flag:

* self-referrals
* multiple accounts controlled by the same authenticated user
* repeated referrals to the same referred account
* repeated qualification from the same payment
* obvious circular referrals
* referral-code manipulation
* duplicate webhook reward processing
* referral rewards for free-plan signup alone
* rewards generated by failed or refunded payments

Use risk signals carefully. Shared IP addresses alone must not automatically prove fraud, but may be logged as a review signal.

Add configurable reward limits.

Do not expose private information about referred users. Show masked or non-identifying status where appropriate.

关于文字、图片、发布的限额规则

请基于当前 VibePin 项目代码和现有 PRD，完成一个简化的 MVP 版本。

本阶段的核心原则是：

* 用户不能选择 AI 文字模型
* 前端不展示模型名称或模型选择器
* 所有用户默认使用同一个文字模型
* 暂时不引入 Credit、Points 或积分系统
* AI 图片、AI 文字和 Scheduled Posts 分别独立统计
* 为以后增加模型选择和 Credit 计费预留扩展能力，但本次不要实现复杂功能

请不要过度设计，本次以稳定、清晰、可上线为目标。

## 一、MVP 模型方案

AI 文字生成统一使用一个默认模型：

```text
默认文字模型：Gemini Flash
```

具体模型 ID 不要直接写死在多个业务文件中。

通过环境变量或统一服务端配置读取：

```env
TEXT_MODEL_DEFAULT=当前项目可正常调用的稳定 Gemini Flash 模型 ID
```

代码示例：

```ts
export const AI_MODEL_CONFIG = {
  text: {
    provider: "google",
    defaultModel:
      process.env.TEXT_MODEL_DEFAULT || "当前可用的Gemini Flash模型",
  },
};
```

模型名称只能存在于服务端配置层。

不要在以下位置写死模型名称：

* 页面组件
* API 路由
* Server Action
* 数据库业务逻辑
* Pricing 页面
* Billing 页面
* 每个生成按钮中
* 多个重复配置文件中

以后更换模型时，应只修改环境变量或一个统一配置文件。

## 二、移除用户模型选择

删除或隐藏当前所有文字模型选择相关功能，包括：

* Model selector
* Gemini / Claude / DeepSeek 模型下拉框
* Standard / Premium 模型选项
* 根据套餐选择模型的逻辑
* 用户偏好的默认模型设置
* 模型价格说明
* 不同模型消耗不同 Credit 的逻辑
* 前端发送 `model` 参数的能力

前端请求不能允许用户自己指定模型。

错误示例：

```json
{
  "prompt": "...",
  "model": "claude-sonnet"
}
```

正确示例：

```json
{
  "prompt": "...",
  "generationType": "pinterest_post"
}
```

模型必须由服务端配置决定，避免用户篡改请求调用更贵的模型。

## 三、暂时不使用 Credit

本阶段不要实现统一 Credit 余额。

不要展示：

```text
Credits
AI Credits
Points
Tokens balance
1 generation = 1 credit
```

也不要将 AI 图片、AI 文字和 Scheduled Posts 混在一个余额里。

MVP 使用三个独立额度：

```text
AI images
AI text generations
Scheduled posts
```

每种功能分别统计、分别限制。

## 四、AI 文字计量规则

一次完整的文案生成请求，计为一次：

```text
AI text generation
```

一次请求可以同时返回：

* Title
* Description
* Hashtags
* Alt text
* Platform-specific copy

以上字段作为一个完整结果，只计一次生成。

扣量规则：

```text
首次成功生成文案：消耗 1 次 AI text generation

点击重新生成：再次消耗 1 次

只重新生成标题：消耗 1 次

只重新生成描述：消耗 1 次

生成失败：不消耗

模型超时：不消耗

内容审核拒绝：不消耗

模型没有返回有效内容：不消耗

用户手动编辑文本：不消耗

保存草稿：不消耗文字额度

发布或定时发布已有文案：不消耗文字额度
```

只有在成功获得并保存有效结果后才能最终扣量。

如果系统采用预留额度机制，失败时必须释放额度。

## 五、AI 图片规则保持独立

AI 图片继续按实际成功生成的图片数量计算。

```text
成功生成 1 张图片 = 消耗 1 张 AI image allowance

一次成功生成 4 张 = 消耗 4 张

部分成功 = 只按成功数量消耗

重新生成图片 = 按新成功图片数量消耗

生成失败 = 不消耗

内容审核拒绝 = 不消耗

上传自己的图片 = 不消耗

使用已有图片发帖 = 不消耗
```

AI 文字生成不能扣 AI 图片额度。

AI 图片生成也不能扣 AI 文字额度。

## 六、Scheduled Posts 保持独立

Scheduled Posts 与 AI 图片、AI 文字完全独立。

推荐计量方式：

```text
草稿：不消耗

预览：不消耗

成功创建一个有效的定时发布任务：消耗 Scheduled Post allowance

重复执行同一个发布任务：不能重复扣量

发布 worker 重试：不能重复扣量
```

检查当前产品对多平台发布的定义。

如果当前套餐定义为每个平台一次发布，则：

```text
同一内容发布到 Pinterest 和 Instagram = 2 次
```

如果当前产品已经定义为一条内容算一次，则沿用当前规则。

不要自行更改已有套餐承诺，只需要保证代码、Pricing 页面和 PRD 定义一致。

## 七、套餐额度

先读取当前项目中已经存在的真实套餐配置，包括：

* 套餐配置文件
* 数据库计划配置
* Creem 产品映射

保留当前已经确定的：

* Connected accounts 数量

不要擅自修改现有套餐数字。

对于 AI text generations：

* 如果尚未定义，建立一个统一配置字段
* 不要将其设置成 Credit

## 八、AI 文字服务封装

    | "title"

同时建立不可变 Usage Event：

```text
usage_events
```

字段：

```text
id
owner_type
owner_id
usage_type
quantity
operation
reference_type
reference_id
idempotency_key
metadata
created_at
```

`usage_type`：

```text

```

`operation`：

```text
reserve

release
reverse

```

要求：

* 原子操作
* 并发安全
* 幂等
* 不允许负数
* 支持失败释放
* 可以审计
* 同一请求不能重复扣量

为 `idempotency_key` 添加唯一约束。

## 十一、正确的文字生成流程

统一流程：

```text
验证登录状态
→ 验证请求参数
→ 验证内容安全
→ 检查 AI text generations 剩余额度
→ 原子预留 1 次额度
→ 调用默认 Gemini Flash 模型
→ 校验返回结果
→ 成功后确认消耗
→ 失败时释放预留额度
```

额度不足时，不得调用模型。

返回统一错误：

```json
{
  "code": "ai_text_limit_reached",
  "message": "You have reached your AI text generation limit for this billing period."
}
```

前端提示：

```text
You have used all AI text generations included in your current plan.

Upgrade your plan to continue generating AI content.
```

## 十四、账号隔离
