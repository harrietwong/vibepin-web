## 0. 本版与 v1.0 的关键差异（必读）

v1.0 业务 PRD 是 0901 规格的重述，它假定问题存在于 Preview runtime `2142aeeb` / `83983889`。
本版做了 v1.0 没做的事：**逐条到当前工作树（`feat/pinterest-production-transition`）里核对代码**。

结论有两个层次：

1. **所有 P0 根因在当前工作树中真实存在**，并且我拿到了行级证据（见开发 PRD §2）。
   它们不是"Preview 上的历史问题"，是本仓库此刻的代码事实。

2. **当前工作树比 0901 PRD 审计的 runtime 更旧**，这是 v1.0 完全没有覆盖的风险：

   | 0901 PRD 假定存在 | 当前工作树实际 |
   |---|---|
   | `PUT /api/pin-drafts` 有两条 422（`destination_not_schedulable` / `destination_unavailable`） | **route.ts 里没有任何 422**（文件停在 07-29） |
   | `explicitPublishDestinations()` | **不存在** |
   | `web/src/lib/studio/runAiGeneration.ts` | **不存在** |
   | `web/src/lib/studio/selectedReferences.ts` | **不存在** |
   | `web/src/lib/studio/generationRecovery.ts` | **不存在** |

   （`/api/generation-jobs/[id]` 路由、`meterGeneration.ts`、`settleGenerationJob.ts` 同样不存在。
   生成目前仍是 `StudioBoard.tsx` + `generateAiVersions.ts` 里的内联客户端流程。）

   **这意味着 0901 PRD §15「代码影响面」不能直接当施工图用。**
   按它派活，执行代理会去改不存在的文件，或者以为 CP-13 只要"改 422 分支"就行——
   而这棵树上 422 还没被引入，要新建整条 per-draft outcome 契约。

   施工前必须先做一次基线裁决（本文档 §7），否则会重演"在旧世系上开分支"的老问题
   （参考记忆 `project_reference_recs_diagnosis_20260827`）。

3. **两处实际缺陷比 0901 PRD 描述的更严重**，这是本版独立复核发现的：

   - **CP-12**：不只是"没有按参考图数量相乘"。服务端 `MAX_IMAGES_PER_REQUEST`
     的默认值是 **2**（不是 4）。也就是说今天连 count=4 都到不了。
     修 UI 侧的算法而不动这个上限，用户仍然只会拿到 2 张。
     （**2026-09-03 更新**：用户已裁决这个上限**不该存在**——
     API 有限制应当排队分批消化，而不是截断用户的请求。详见 §3.1 CP-12a。）
   - **CP-14**：0901 PRD 说的是"卡片 chip 与发布确认之间有漂移"。
     实测**不是漂移**——卡片和发布路径**各自独立**地凭空造了一个 Pinterest destination。
     两边都看不到"零目标"这个状态。真正的缺陷是：一个从未选过发布目标的草稿，
     和一个真的发往名为 "Pinterest" 的 Board 的草稿，**在界面上完全无法区分**。
     这比"两边不一致"更难被用户察觉。

## 1. 产品愿景与本期目标

Create Pin 的目标不是继续增加入口和状态提示，而是让用户从"选素材"到"生成、编辑、排期、
发布前准备、失败恢复"，**始终操作同一条可追踪的 Content**。

本期只解决一件事：**让 UI 说的话等于系统实际做的事。**

当前所有 P0 的共同形状都是「显示与事实脱节」：

- 绿色 toast 说"正在生成 2 个"，红色 toast 同时说"未生成任何 Pin" —— 显示与事实脱节
- 卡片显示 `Home Decor` Board chip，发布确认却判定"零发布目标" —— 显示与事实脱节
- 同步状态显示"已同步"，canonical 表里其实没有这行 —— 显示与事实脱节
- 用户选了多张产品图和风格图，UI 承诺一个数，后台上限却把请求截成 2 张 —— 显示与事实脱节
- 关闭抽屉再打开，风格参考图消失 —— 系统丢了用户明确表达过的意图
- 换台电脑登录，自己的草稿不见了 —— 数据没有真正跟着账号走

**不做的事**：不新增功能、不改视觉风格体系、不建第二套 Product/Reference/job/usage/publish 事实源。

## 2. 用户故事与验收口径

每条故事都给出「用户看到什么算成功」，不是「代码里有没有这个函数」。

### US-1 生成反馈可信

> 作为创作者，我点了生成之后，我要能一眼看懂当前到底是"在跑""跑完了""失败了"还是"结果没确认"，
> 而不是同时看到两条互相矛盾的提示。

**验收**：一次生成从头到尾**只有一条 toast**，它原地从"正在生成"变成终态。
全失败时不能还留着绿色的"正在生成"。失败后我还能重试，重试不会重复扣量。

### US-2 我选的东西不会凭空消失

> 作为创作者，我挑了两张风格参考图、写了创意方向、选了模型和数量，
> 关掉抽屉再打开，或者生成失败之后，这些选择应该还在。

**验收**：普通关闭、生成、生成失败、页面刷新之后重开抽屉，商品图 / 参考图 / 方向 /
模型 / 格式 / 数量**全部回填**。只有我明确点"新建"或删除，才清空。

### US-3 数量承诺被兑现

> 作为创作者，我选了 3 张产品图和 2 张风格参考图，
> 系统应该把它们两两组合，给我 6 张图 —— 每个产品配每种风格各一张。
> 不该因为后台有个上限，就悄悄只给我 2 张。

**验收**（2026-09-03 用户改写需求，取代旧的"参考图×每组几张"口径）：

- **数量 = 产品图数 × 参考图数**（矩阵组合），UI 明确显示这个总数
- **点下生成后立刻**出现全部占位卡，**出一张填一张**，不等全部跑完
- 后台 API 有限制就**排队分批跑**，**不截断**用户的请求
- 界面可选数量**不按套餐分级**
- 数量特别大时（如 80 张）先提醒确认，但**不阻止**
- 哪个产品×哪种风格产出哪张结果是稳定可归属的；整批只扣一次量

### US-4 发布目标不撒谎

> 作为创作者，卡片上显示的发布目标，必须就是我点发布时真正会发过去的地方。
> 如果我其实还没选，就应该明白地告诉我"尚未选择发布目标"，而不是显示一个看起来能发的 Board。

**验收**：只有保存过明确 provider + 账号 +（Pinterest Board / Facebook Page）的草稿，
才显示真实 destination chip。只有旧 Board/category 的草稿显示中性的"尚未选择发布目标"，
点它直接打开选择器。点发布如果被前置校验拦下，**必须在卡片上留下持久的、说得清的原因**，
不能只闪一个 toast 或者毫无反应。

### US-5 我的草稿真的被保存了

> 作为创作者，同步状态说"已保存到服务器"，就应该真的在服务器上。
> 如果某一条因为发布目标失效被拒绝，不应该连累同一批里其他正常的草稿。

**验收**：一批里 1 条合法 + 1 条不合法，合法那条**持久化成功**，
不合法那条单独显示"需要处理"并指出是哪个 Pin、要做什么。
修好之后只重试坏的那条。确定性拒绝**不会**无限重试。

### US-6 数据跟着账号走，且不会串号

> 作为创作者，我换一台电脑、换个浏览器登录，我的草稿应该还在——数据是跟着我的账号的，
> 不是跟着某台机器的。同时，我登出之后同事用同一台电脑登录，
> 他不该看到我的草稿，系统也不该拿他的身份去提交我的待同步内容。

**验收**（两条都要过）：
- **跟随账号**：在浏览器 1 建草稿并等同步完成 → 用**全新浏览器**登录同一账号 → **草稿都在**，
  且不出现"先空一下再填上"的闪烁
- **不串号**：A 登出 → B 登录，B 侧对 A 的内容产生 **0 次请求、0 个 job、0 次扣量**，
  界面上看不到 A 的任何内容。A 重新登录后，自己的待同步内容还在。

> 说明：服务器端**已经**按账号存草稿并支持回读（已实测），
> "换浏览器看不到"的真实原因是同步链路被一条坏草稿卡死了——
> 修好 CP-13a/b 的逐条同步，这个问题就解决了大半。

### US-7 界面不崩

> 作为创作者，反复开关批量编辑不应该白屏。

**验收**：批量编辑 关→开→关、单选→双选→清空、刷新，控制台 **0 个 React #310**。

## 4. 关键业务规则（裁决，不是建议）

1. **不恢复任何默认兜底。** 不默认 Pinterest、不默认账号、不默认 Board。
   宁可显示"尚未选择"，也不猜。猜错的代价是发到错误的账号上，不可撤销。

2. **一条 Content 多渠道发布只计一次量。** UI 重开、replay、重试都不改变这个身份。

3. **`unknown` 不等于失败。** 提交结果未知时，保留可恢复 intent，
   **禁止**新建 job / 占位 / 预留 / 扣量。刷新和重试必须先对账。
   只有服务端证明原次已终态失败且无活跃 job，用户明确点"重试"才允许新建子 intent。

4. **`PUT /api/user-store` 返回 202 不能算作草稿已同步。**
   canonical 事实源是 `pin_drafts`，UI 不得用前者冒充后者显示"所有更改已同步"。

5. **部分成功不能伪装成全成功或全失败。** 逐目标显示，成功的腿永不重发。

6. **TikTok 前端隐藏，服务端也必须 fail closed。** 旧草稿不能绕过。

7. **测试库与生产库永久分离。** 本期一切验证只在测试库 `snulmwprsahzqvdbyenc`。
   任何写操作前先打印 project ref 并断言 ≠ `jaxteelkecvlozdrdoog`。

| 词 | 含义 |
|---|---|
| Content | 用户创作的一条内容，可 fan-out 到多个平台，计量一次 |
| destination | 一个明确的发布目标 = provider + connectionId + 账号身份 +（Board/Page） |
| intent | 用户一次明确意图的稳定标识，重试/刷新/replay 都复用它 |
| group / slot | 生成的二维结构：group 对应一张参考图，slot 是组内第几张 |
| outcome | 逐条草稿的同步结果：applied / stale / rejected / deferred |
| canonical | 唯一事实源。`pin_drafts` 是草稿的 canonical，`user-store` 不是 |
| owner-scoped | 按 `ownerUserId + workspaceId` 隔离，A/B 不串 |
