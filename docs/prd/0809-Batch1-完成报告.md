## 1. Audit 发现的真实原因

**连接状态忽隐忽现(本轮 blocker)**:`PublishDestinations.load()` 把
`/api/social/connections` 和 3 秒超时赛跑,输了当失败 → 三个平台全画成 "Not connected"。
该接口要读多个 provider,**冷调实测 4.1 秒**,发布又恰好在抽屉重读时加重负载。
同文件下方的 Pinterest 信号**早修过同一个 bug**(注释写着),IG/FB 没跟上。

**更深一层**:Pinterest 状态 API **覆盖**共享数据,Settings 与抽屉能对同一账号算出不同答案,
且覆盖的 "not_connected" 分支能推翻 canonical 的 "connected"。

**账号显示成 `@5522278466b6972`**:Pinterest `/user_account` 返回
`business_name` / `profile_image`(实测字段全表已核),parser 两处都丢弃;
**下游还有两处又丢一次** —— 连接投影用 `@${username}` 重拼、token 刷新路径每次覆盖显示名。

**"Publishing not yet wired for this platform."**:`official.ts:71` 的内部措辞,
服务端**没有任何能力检查**,陈旧选择或直接调 API 就能让它变成客户看到的发布结果。

**Posted 详情两个真缺陷**:账号读的是**当前连接**而非当初发布的账号(换账号后历史结果自己改名);
没记录 handle 的平台**整行被过滤掉**(发布了却无痕迹)。
