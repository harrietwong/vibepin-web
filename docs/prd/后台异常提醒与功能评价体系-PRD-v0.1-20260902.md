## 1. 目标与非目标

**目标**

1. 创始人**不打开后台**也能在 24h 内知道有客户被卡住(驾驶舱 PRD §5 的既定目标,目前完全依赖「记得去看」)。
2. 回答「每个功能有没有人用、值不值得继续投入」,用**已有埋点**,不新增打扰用户的调研。
3. 全程沿用数据诚实文化:三态区分、推断值标注、绝不把「没采集」显示成 0。

**非目标**(继承驾驶舱 PRD §4)

- ❌ 不做告警平台 / 规则引擎 / 值班轮转 —— 一个人的团队不需要 PagerDuty
- ❌ 不做产品内评分弹窗、NPS —— n=4 时回收率本身又是个小样本问题,且打扰唯一的真实客户
- ❌ 不新建后台页面(按准入标准自我审查后否决,见 §3.4)
- ❌ 不做自动化干预(自动发邮件给用户、自动送 credit)—— 用户量小时「手动干预本身就是用户调研」

## 2. A 部分:异常主动提醒

### 2.1 推什么(P0 只推 3 类)

准入标准:**确凿 + 紧急 + 能导向一次干预动作**。

| 阻塞类型 | 推? | 理由 |
|---|---|---|
| **发布失败(exact)** | ✅ 推 | 有服务端事件为证,非推断;客户的内容没发出去,越晚发现越糟 |
| **Pinterest 断连** | ✅ 推 | 状态明确;不重连则后续全部排期失效 |
| **生成连续失败 ≥2 次** | ✅ 推 | 有 `pin_generations.status='failed'` 为证;客户正在撞墙 |
| 发布失败(inferred) | ❌ 不推 | 由草稿状态推断,误报率未知。**留页面** |
| 注册未激活 / 连接未创作 | ❌ 不推 | 是运营节奏问题不是故障,48h/72h 才触发,没有「立刻」的意义。**留页面** |
| 配额 ≥80% | ❌ 不推 | 是商机不是故障(Codex 已裁定不得混入故障名单)。**留页面** |
| 用量 anomaly(重复行 / 负值 / 未知套餐) | ❌ 不推 | 数据质量问题,影响后台自身可信度而非客户体验。**留页面** |

**本节的核心判断:宁可漏报,不可误报。** 页面本身是兜底(创始人每天会打开一次),而误报的代价不可逆 —— 推三次假警报之后,第四次真警报也不会被认真看。在 n=4 的体量下,漏报晚几小时被发现的成本,远低于失去对提醒的信任。

### 2.2 阈值:不用任何百分比

**n=4 时百分比毫无意义** —— 1 个用户失败 1 次就是 100%。

全部沿用 `adminActionCenter.ts` 已有的判定口径(绝对事件计数 + 时间窗口),**不新写一套**:

- 发布失败:24h 内有失败且此后无成功
- 断连:`needs_reconnect = true OR disconnected_at IS NOT NULL`
- 生成连续失败:24h 内 ≥2 次失败且无成功

**这条同时是防重复实现的约束**:告警判定必须调用 `getActionCenter()` / `getUserBlockers()`,不得复制一份判定逻辑 —— 两套逻辑迟早漂移,届时页面和邮件会互相矛盾,而创始人无从判断该信哪个。

### 2.3 去重:状态转换触发,不是每日重发

**规则:只在「无 → 有」的转换时推一次。**

同一个 `(userId, blockerType)` 只要持续存在,就**不再重复推送**;直到它消失(转为「无」),下次再出现才算新告警。

实现(应用层去重,因 F3 无 DB unique 约束):

1. 每次 cron 跑完,拿到当前阻塞集合 `S_now`
2. 查 `admin_audit_events` 里 `action = 'alert.blocker_notified'` 且未被后续 `cleared` 抵消的记录,得到 `S_sent`
3. **新增** = `S_now - S_sent` → 推送,并写一条 `alert.blocker_notified`
4. **已消失** = `S_sent - S_now` → 写一条 `alert.blocker_cleared`(不推送,仅留痕,让下次同类问题能重新触发)

`target_type = 'user_blocker'`,`target_id = <userId>:<blockerType>`,`metadata` 存 evidence 摘要。

**零新表** —— 复用 v34 审计表,只新增两种 `action` 值。

### 2.4 送达:P0 只用邮件

- 收件人:见 §6 待裁决 1
- 发送:复用 `sendEmail()`。**未配置 `RESEND_API_KEY` 时它返回 `skipped:true` 且不抛错** —— 本地开发天然静默,无需额外分支
- **一次 cron 一封汇总邮件**,不是一个阻塞一封(防收件箱轰炸)
- 内容:每条含用户邮箱、阻塞类型、首次发现时间、原因摘要、建议动作、深链到 Customer 360 —— 即驾驶舱名单的邮件版
- Slack / 移动推送:**P2**,等邮件被验证真的有人看之后再说

### 2.5 落点与触发

| 项 | 落点 |
|---|---|
| 判定复用 | `web/src/lib/server/adminActionCenter.ts`(**不改**,只调用) |
| 新模块 | `web/src/lib/server/adminAlerts.ts`(去重 + 组装 + 发送,纯逻辑可测) |
| 触发 | `web/src/app/api/cron/admin-alerts/route.ts`,**照抄** `expire-reservations` 的鉴权:`CRON_SECRET` bearer,缺配置返回 503 拒跑,不匹配返回 401 |
| 调度 | VPS crontab,**不是 `vercel.json` crons**(项目既有约定)。频率 P0 = 每日一次 |

**为什么每日一次而不是每小时**:创始人每天看一次后台,小时级推送只会制造噪音;且驾驶舱 PRD 的目标是 <24h 发现,每日一次即达标。

### 2.6 A 部分验收标准

- [ ] 构造一个新增阻塞 → 收到一封邮件,含该用户邮箱 / 类型 / 建议动作 / 深链
- [ ] **同一阻塞持续存在 → 第二天不再收到**(去重生效)
- [ ] 阻塞消失后再次出现 → 重新收到(cleared 记录让它能重新触发)
- [ ] 一次 cron 有 3 个阻塞 → 只收到 1 封含 3 条的邮件
- [ ] 未配置 `RESEND_API_KEY` → cron 正常完成、日志有记录、**不报错**
- [ ] `CRON_SECRET` 缺失 → 503;错误 secret → 401
- [ ] **邮件发送失败不影响 cron 完成**(best-effort),失败摘要写入审计
- [ ] 判定结果与 `/admin/today` 页面**逐条一致**(证明没有第二套判定逻辑)
- [ ] **变异验证**:删掉去重条件 → 重复推送的测试必须变红

## 3. B 部分:功能评价体系

### 3.1 边界:不与视觉闭环重复

`0831` 报告已覆盖「用户对**生成结果**的评价 → 反推视觉模型」。本部分回答的是另一个问题:**每个功能有没有人用、值不值得继续投入**。

### 3.2 三层信号(全部复用已有埋点,零新增打扰)

| 层 | 来源 | 现状 |
|---|---|---|
| **隐式行为** | `analytics_events` 20+ 事件:`generation_kept` / `generation_deleted` / `direction_rejected` / `reference_rejected` / `regenerate_clicked` / `draft_published` / `draft_scheduled` | ✅ 代码齐备,**待部署后产数据** |
| **结果指标** | `pin_generations`(服务端写)、`analytics_events` 的发布三事件、`usage_accounts` | ✅ 齐备 |
| **显式评价** | **不做产品内弹窗**;依托工单系统 + 创始人主动沟通 | 见 §3.5 |

### 3.3 采用漏斗:后三段现在就能算

对每个有落库痕迹的功能,定义:

```
曝光 → 首次使用 → 重复使用(≥2 次)→ 留存(跨周仍在用)
```

- **后三段可直接从 `analytics_events` + `pin_generations` 派生**,不需要新埋点
- **「曝光」段系统性缺失**(从未埋过负例:用户看到了但没点)。**P0 不补** —— 补它要在每个功能入口加曝光埋点,改动面大且当前 4 个用户下信息量极低。**在 UI 上诚实标注该段为「未采集」,不显示为 0**

### 3.4 呈现:不新建页面

按驾驶舱 PRD §1 的准入标准(「不能导向一次干预动作的信息不进后台」)自我审查:

- 一张「功能采用率总览」图表**不能告诉创始人今天该帮谁** → 不做
- 但「某功能连续两周零使用」**能导向一次决策**(砍掉 / 改进 / 引导)→ 值得知道

**结论:P0 不新建页面,只在 `/admin/today` 底部加一行「功能采用摘要」**,且只在**有异常信号时**出现(某功能零使用、或使用量断崖)。无异常时不占版面。

### 3.5 显式评价:P0 不做弹窗

理由:

1. n=4 时,弹窗回收率本身是个新的小样本问题(2 个人回答 = 「50% 满意度」?毫无意义)
2. 唯一的真实客户注册 39 天从未连接 Pinterest —— **他需要的是一封人写的邮件,不是一个弹窗**
3. 驾驶舱 PRD 明确:用户量小时「手动干预本身就是用户调研」

**替代方案:** 阻塞名单 + 告警邮件已经给出「该找谁聊」的名单,创始人直接联系;工单系统(`support_tickets`)是现成的记录载体。

### 3.6 诚实性口径(硬规则)

- **不画百分比**,n<10 时一律显示绝对数(「3 个用户中 1 个用过」)
- **不显示「满意度:N/A」** 这类暗示「我们测量过」的格式;没测就写「未采集」
- **不做单样本行为归纳**(「唯一的用户删掉了这张图」≠「用户不喜欢这种风格」)
- 沿用 `adminUsage.ts` 的三态范式:`measured` / `not_measured` / `unavailable` —— **该三态目前只在用量卡片用过一次,应成为全后台统一范式**

### 3.7 一个必须验证的悬空假设

`generation_judged` 事件已在生产落库 8 维 AI 质量分(safety / realism / sceneFit / artifacts / composition / pinterestFit / productPreservation / overall),且 `topPick.ts` **已经在用它给用户展示 “Top pick” 徽章**。

**但这个分数与「用户实际会不会采用」的相关性从未验证过。** 可能高度相关(那它是好指标),也可能接近 0(那基于它的排序推荐建立在沙子上)。

**验证方法**(零新基建,一次性分析,不做常驻页面):

1. 取所有 `generation_judged` 事件的 `overall` 与 8 个分维度
2. 与同批次生成结果的最终命运交叉:`generation_kept` / `generation_deleted` / 是否最终 `draft_published`
3. 产出一句可验证的结论:「judge overall 与最终发布率的方向性关系是 [强 / 弱 / 样本不足]」,**并说明基于多少条样本**

**前置条件:部署后积累足够样本。** 样本不足时结论必须是「样本不足」,不得强行给相关系数。

### 3.8 B 部分验收标准

- [ ] 对每个纳入的功能,能给出后三段的**绝对数**(不是百分比)
- [ ] 「曝光」段显示为「未采集」,**不是 0**
- [ ] 无异常信号时,`/admin/today` 不出现功能采用摘要(不占版面)
- [ ] 某功能零使用 → 摘要出现且指明是哪个功能
- [ ] 独立 SQL 对账:按本 PRD 定义重写查询,与页面数字一致
- [ ] §3.7 的相关性验证给出结论**或**明确的「样本不足 + 当前样本数」

## 5. 风险

| 风险 | 缓解 |
|---|---|
| **告警疲劳** | 只推 3 类确凿异常;状态转换去重;每日一封汇总。**这是本 PRD 最大的失败模式** —— 一旦创始人开始无视邮件,整个功能归零 |
| **两套判定逻辑漂移** | 告警必须调用 `getActionCenter()`,不复制判定;验收标准含「与页面逐条一致」 |
| **误报侵蚀信任** | 只推 exact 不推 inferred;宁可漏报 |
| **邮件发送失败静默** | 失败摘要写入 `admin_audit_events`,后台可见;但**不因发送失败中断 cron** |
| **小样本过度解读** | §3.6 硬规则:不画百分比、不做单样本归纳 |
| **judge 分数可能无效** | §3.7 明确它是**未验证假设**,验证前不扩大其使用范围 |
| **部署前无法验收 B 部分** | 已在 §0.2 F4 标注;实施可先行,验收等上线 |
