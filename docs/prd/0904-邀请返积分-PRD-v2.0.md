## 1. 一句话

老用户把 VibePin 推荐给朋友,**朋友完成第一笔真实付费后**,双方各得一笔**通用积分**。
积分在套餐配额用尽后自动使用,**可跨月,最长有效 180 天**。

## 2. 为什么是这个形态

### 2.1 触发点绑死付费 —— 反欺诈的地基

调研中最硬的否定性证据:**没有找到任何"裸注册即发主奖"的正经产品。**
- Tailwind(最直接的 Pinterest 排程竞品):好友 upgrade to a paid plan 才发(官方 KB 原文)
- Dropbox:注册 + 装桌面客户端 + 登录 + 验邮箱,四步缺一不可

我们比 Dropbox 危险得多:Dropbox 送磁盘空间(边际成本≈0),
**我们送真金白银的推理成本**。绑定付费后刷号者必须真掏钱,经济上不成立。

### 2.2 通用积分的定价逻辑(v2.0 修正)

【实测】Tailwind 定价页原文:
> "Credits are Tailwind's universal currency for actions like scheduling Pins,
> running keyword searches, and boosting Pins."

**"通用"= 一个钱包可买多种动作,不代表所有动作同价。**

**⚠️ v1.0 的错误(Codex 指出,已复核成立):**
v1.0 写"1 积分 ≈ $0.005 成本上限" —— **不成立**。
备用模型 `gpt-image-2` 是 $0.10/张,10 积分对应 **$0.01/积分,是 2 倍**。

**⚠️ 另一处措辞错误:**
v1.0 说 10:1 是"与真实成本对齐" —— 实际成本比是 **29.4:1**。
**10:1 是有意补贴图片的产品决策,不是成本等价。** 必须这样定义,不能自欺。

### 2.3 平台条款红线(已抓原文核实)

| 奖励触发点 | Pinterest | Meta | 裁决 |
|---|---|---|---|
| 邀请好友注册我们的产品 | 未禁止 | **明确允许** | ✅ 做 |
| 奖励"连接社交账号" | 未明文禁止 | 明确允许 | ⚠️ 保守起见不做 |
| **奖励"发 Pin / 发帖"** | **明确禁止** | **明确禁止** | ❌ 绝不做 |
| 奖励好评/测评 | — | — | ❌ 绝不做(FTC 明文禁止) |

原文:
- Pinterest 开发者指南 "What not to do":
  > "Requiring or incentivizing engagement. For example, don't require end users to create
  > or save a Pin to a certain website, or to save a certain Pin in exchange for a benefit."
- Meta Platform Policy 3.2:禁止 "incentivize people to post content";
  明确允许 "reward people for using Facebook to login" 与 "referral based rewards"

**硬约束:奖励只绑定我们自己的商业事件,永不绑定平台侧内容动作。**

## 5. 核心规则

### 5.1 积分消耗(v2.0 重大修订)

| 动作 | 消耗积分 | 说明 |
|---|---|---|
| 生成 1 张 AI 图 | **10 积分** | 默认模型成本 $0.05 |
| 生成 1 次 AI 文案 | **0(本轮不消耗)** | 见下方说明 |

**⚠️ 为什么文案暂不消耗积分(Fable 与 Codex 独立得出同一结论):**

实测 `web/src/app/api/ai-copy/route.ts` **只 `import recordUsage`,没有 `checkAllowance`**;
且所有套餐的 `ai_text_generation` 上限恒为 `null`(只计量、从不限额)。

**后果:即使配上 `CREDIT_COST.ai_text_generation = 1`,也永远不会有文案请求扣到积分** ——
因为根本没有"套餐用尽"这个状态。这是**阻断性产品矛盾**。

三个选项(**需你裁决,见 §11**):
- **A(建议)**:文案不消耗积分,积分只用于图片。改动最小,且文案成本 $0.0017 收 1 积分($0.005)本就**倒挂**。
- **B**:给文案设套餐内额度,超出才扣积分 —— **削减既有权益**,老用户会投诉,需公告。
- **C**:引入需要积分的高级文案动作 —— 净新增功能,工作量最大。

**在裁决前:代码路径全部就位,`CREDIT_COST.ai_text_generation = 0`。**
**文案上绝不能宣传"可换 100 次文案"**(Codex:在定义真实消费场景前不得如此宣传)。

### 5.2 奖励数值与成本口径(v2.0 全面重写)

| 角色 | 通用积分 |
|---|---|
| 邀请人 | +100 |
| 被邀请人 | +100 |

**成本口径(v1.0 的"首月回本"结论已删除):**

| 场景 | 单笔转化成本 | 占 Starter $19 标价 |
|---|---|---|
| 默认模型全部兑换 | **$1.00** | 5.3% |
| **备用模型全部兑换** | **$2.00** | **10.5%** |

**必须诚实的四点(Codex 指出,已复核):**
1. $19 是**标价**,不是扣除 MoR 费用、税费、折扣后的**贡献收入**;
2. 文案 $0.0017 是**典型请求估计**,不是有 token 上限的最大值;
3. 好友可能**用完积分后退款**,Creem 退款仍保留原交易处理费;
4. "每人每月 10 笔"只限制**单账号**,批量创建邀请人账号可横向绕过。

**正式表述:**
> 当前默认模型下,每个付费转化的最大奖励推理成本为 $1,约占 Starter 标价的 5.3%;
> 备用模型路径为 $2。最终贡献利润需按净收款和实际兑换率计算。

**因此必须增加(F8):**
- **全局日/月发放预算上限**
- **异常熔断开关**(发放量突增时自动停发)
- **实际兑换成本监控**(不是发放量,是真正被消耗掉的成本)

**备用模型的处理(三选一,需裁决,见 §11):**
- (a) 成本预算按 $2/转化计;
- (b) **积分支付的生成禁止切换到更贵的备用模型**(建议);
- (c) 图片价提高到 20 积分。

### 5.2b ⚠️ 被邀请人的奖励可能几乎没有价值(待裁决)

奖励只在付费后发,但**付费用户的套餐配额本来就够用**,积分只在套餐耗尽后才消耗:

| 被邀请人套餐 | 月配额 | 100 积分(=10 张)的相对价值 |
|---|---|---|
| Starter | 150 张 | +6.7% |
| Pro | 800 张 | **+1.3%** |
| Business | 3000 张 | **+0.3%** |

被邀请人恰恰是我们要说服掏钱的人,给他一个用不上的奖励,**"双边奖励"实际是单边的**。

Codex 补充:若套餐用户通常用不完配额,**奖励感知价值会明显低于标称的"10 张图"**。

方向(需裁决):
1. 被邀请人改发**首月折扣** —— 但实测仓库**完全没接入 Creem 折扣券**(grep discount/coupon/promo 零命中),是净新增工作;
2. 被邀请人奖励改在注册时发 —— **破坏付费触发的反欺诈地基,不建议**;
3. **维持现状**,承认主要驱动力来自邀请人 —— 但**文案必须诚实**,不能把 100 积分说得像很大好处。

### 5.3 触发与时序(v2.0 重大修订)

```
邀请人分享链接
   └→ 好友点击 ?ref=CODE(服务端写 30 天 HttpOnly cookie)
        └→ 注册(落 pending 归属,不发奖)
             └→ 好友完成【第一笔金额>0 且已成功收款】的交易   ← 唯一发奖时点
                  └→ 同一事务内:双方各 1 个积分批次 + 上限占位 + referral 置 converted
                       └→ 退款/拒付 → 按比例追回未消费部分
```

**⚠️ 为什么不能用 `subscription.active`(Codex 指出,复核后发现更严重):**

Creem 将 `subscription.active` 定义为**新订阅创建**,`subscription.paid` 才表示已收款。
更关键的是,**实测我们自己的 `creemStatusGrantsAccess` 包含 `trialing`**:

```ts
return status === "active" || status === "trialing";   // creemStore.ts:311
```

→ 用 `active` 发奖会**给免费试用发奖,零收入**。

**发奖资格必须是:金额 > 0 且已成功收款的首笔交易。**

**⚠️ 防重复发奖(每月续费都会触发 `paid`):**
既有注释写明 `paid` 是 "the paid/**renewed** signal" —— 每月续费都触发。
**两道防线缺一不可:**
1. 只认 `referrals.status='pending'`,发奖后立即置 `converted`;
2. `idempotency_key` UNIQUE 约束。

**验收必须包含:同一订阅连续 3 次 `subscription.paid`,只发一次奖。**

### 5.4 归属规则

- **Last-touch**:多次点击以最后一次为准
- **归属窗口 30 天**:服务端设置 `Secure / HttpOnly / SameSite=Lax / Max-Age=30d` 的 cookie
  > ⚠️ 不可照抄既有 `vp_next` 的 `max-age=600` —— 那会把 30 天窗口砍成 10 分钟(Codex 指出)
- **一个 referee 一生只归属一次**(防退订重订刷奖)
- **注册后 90 天内完成首付才有效**(v2.0 新增 —— 否则 pending 可无限期转化)
- 归属在注册时固化,不可变更

### 5.5 积分性质与 FEFO 批次模型(v2.0 重大修订)

- **可跨月,最长有效 180 天**(v1.0 的"用完为止"与过期自相矛盾,已改)
- **扣减顺序:先套餐配额,再积分**(套餐本就月清,先用不浪费)
- 无现金价值、不可转让、不可提现

**⚠️ 必须用 FEFO 批次(lot),不能用 `SUM(delta)`(Codex 指出,已采纳):**

`SUM(delta)` 无法回答"某次消费用了哪一笔发放",因此**算不准某笔到期奖励的未消费部分**,
在并发、退款、多批次到期时都会出错。

**正确模型:**
- 每次发放 = 一个 lot:`granted_quantity` / `remaining_quantity` / `expires_at` / `source_type`
- 消费时锁定该用户批次,**按最早到期优先(FEFO)**分配,写 allocation 记录
- 过期:把该批次的**精确 `remaining_quantity` 置零**
- 退款:只追回对应批次未消费部分;已消费记 `unrecovered_quantity`,**不产生负余额**
- 当前余额 = 未过期 lot 的 `remaining_quantity` 求和
- 每日 job 只做状态整理与通知,**不承担余额正确性**

> 正名:是 **FEFO**(先到期先出),不是 FIFO。
> 因此页面不能只写"180 天内有效",应显示"最早有 N 积分于 X 日到期"。

`source_type` 区分 referral / 运营补偿 / 未来购买积分 —— 未来若售卖积分涉及递延收入与
breakage,不能与促销积分混账。

### 5.6 与订阅生命周期的交互

| 事件 | 积分怎么办 | 理由 |
|---|---|---|
| `canceled` / `expired` / `paused`(**未退款**) | **保留到原到期日** | 钱收过了,推荐真实 |
| `update`(升级/降级) | **不变,也不重发** | 与套餐无关 |
| `paid`(每月续费) | **不再发奖** | 见 §5.3 幂等 |
| `refund.created`(**部分退款**) | **按退款比例**追回未消费部分 | Creem 支持部分退款 |
| `dispute.created`(拒付) | **100% 追回**未消费部分 | |

**关键区分:退订 ≠ 退款。** 退订保留,退款追回。

**追回不设 30 天限制** —— 任何时候收到针对资格交易的事件都要处理(Codex 指出)。

**必须处理 webhook 乱序**:退款先到、付费后到时,**不得重新发奖**。

### 5.7 上限(v2.0 修订)

- **邀请人**:每自然月最多因邀请获得 **10 笔**奖励
- **被邀请人:不受该上限影响,始终兑现**

> ⚠️ v1.0 写"达上限后不再发放"但页面承诺"双方各得" —— **这是宣传不实**(Codex 指出)。
> 被邀请人不该为邀请人的上限买单。

- 达上限后邀请人侧不再发放,**页面明示**

## 6. 反欺诈与资金安全

### 6.1 零成本基线

| 措施 | 拦什么 |
|---|---|
| 自荐拦截(user_id + 规范化邮箱) | 自己邀请自己 |
| 一个 referee 一生只归属一次 | 退订重订刷奖 |
| 邀请人每月 10 笔上限 | 单账号批量套利 |
| 一次性邮箱域名黑名单(开源列表) | 一次性邮箱注册 |
| 退款/拒付按比例追回 | 付了再退的套利 |
| 条款保留取消资格与追回权利 | 兜底 |
| **全局日/月发放预算 + 熔断**(v2.0 新增) | **上限绕过、批量邀请人账号** |

**暂不采购**付费风控(邮箱验证 ~$10/千次、设备指纹 $99/月起)——
付费触发下性价比不足。这类信号应做**风险评分**而非硬拦截(共用设备的家人、VPN 用户会误伤)。

### 6.2 ⚠️ 扣款必须原子(v2.0 新增,阻断项)

**问题**:v1.0 的"预检余额 → 调 LINAPI → 成功后扣积分"不安全:
- 并发请求可同时通过预检 → **余额被扣成负数**
- 扣款失败时用户**已经拿到图片** → 白送算力
- 实测既有 TTL lock 在 `os.tmpdir()`(serverless **每实例一份**),**无法全局互斥**,
  且它在 allowance 检查**之后**才获取

**必须改为:调用供应商【之前】做数据库原子预留**
- 单个事务内完成:套餐溢出计算 + 积分预留(FEFO 锁定批次)
- 按 `request_id` 幂等
- 失败释放预留;**部分成功按实际图片数结算**
- **套餐内请求继续 fail-open**(不查积分,维持既有不变量)
- **需要积分支付的部分,积分系统故障时 fail-closed** —— 宁可拒绝,不可白送付费算力

## 7. 页面与文案

### 7.1 邀请中心 `/app/referrals`
- 邀请链接 + 复制
- 累计邀请人数 / 累计获得积分 / **当前可用余额** / **最早到期批次**

## 12. 验收标准

1. 未通过邀请链接注册者不产生归属与奖励
2. 好友仅注册未付费 → 不发奖,状态"已注册待付费"
3. **好友进入 trialing(免费试用)→ 不发奖**
4. **好友首笔金额>0 且收款成功 → 双方各到账 1 个积分批次**
5. **同一订阅连续 3 次 `subscription.paid` → 只发一次奖**
6. 自荐(同 user / 同规范化邮箱)→ 拦截
7. **部分退款 → 按比例追回未消费部分;拒付 → 100% 追回**
8. **已消费部分不追回,余额永不为负**
9. **退订/降级/暂停但未退款 → 积分保留到原到期日**
10. **webhook 乱序(退款先到)→ 不重新发奖**
11. 套餐用尽后可用积分继续出图;套餐内不扣积分
12. **并发 5 个生成请求 → 余额不为负,扣减总额正确**
13. **积分系统故障:套餐内请求照常;需积分的请求被拒(不白送)**
14. 只按 `successfulImageCount` 扣积分,失败不扣
15. **FEFO:先消耗最早到期的批次**
16. **批次到期 → 精确置零 `remaining_quantity`,不影响其他批次**
17. **邀请人达月上限 → 邀请人不发,被邀请人照发**
18. 归属 cookie 有效期为 **30 天**(非 600 秒)
19. **注册后超 90 天才付费 → 不发奖**
20. 18 语言齐全,`validate:i18n` + `validate:i18n-coverage` 通过
21. 全流程无"连接账号/发帖/好评得奖励"的入口或文案
22. **文案不出现美元价值,不出现"可换 N 次文案"**(除非裁决 1 选 B/C)
