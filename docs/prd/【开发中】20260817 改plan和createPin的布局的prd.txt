# VibePin Create Pins / Plan / Scheduling 一致性与失败恢复 PRD V1.0

**版本状态：产品评审稿 / Audit-ready**
**日期：2026-08-16**

本 PRD 聚焦：

* Create Pins 信息架构
* Plan 入口与响应式布局
* Scheduled Pin 多平台发布
* 默认发布目标
* Pinterest Board 记忆
* Unscheduled 数据语义
* Failed 图片与错误文案
* AI 创建入口

本 PRD 不重新定义 Social Account 底层架构，不取代 Social Accounts PRD 中已经确认的账号身份、Reconnect、多账号和 Workspace 隔离原则。

在 Audit 获批前，不允许大范围实施。

---

# 1. 背景与当前问题

当前 Create Pins 已同时承担：

* 内容创建
* 编辑
* 排程
* Weekly Plan
* 发布
* 多平台发布
* Posted
* Failed
* AI 编辑

但当前界面出现了多处概念混用。

主要问题：

1. `Plan` 与 `All / Unscheduled / Scheduled / Posted / Failed` 放在同一状态栏，但 Plan 并不是内容状态。
2. Scheduled Pin 是否真正向多个选择的平台执行发布缺少清晰的产品规则。
3. 用户下一次排程时，之前使用过的 Pinterest Board 没有合理复用。
4. Plan 右侧 `Unscheduled Pins` 出现已经发布的内容。
5. Plan 底部又出现 `Added to plan · assign a date`，与 Unscheduled Pins 概念重复。
6. Plan 占用整个主页面，但 Create Pins 本身还有大量创建和编辑工作，页面切换成本较高。
7. AI 创建入口和 AI 编辑操作层级仍可优化。
8. Failed 页面存在大量重复、技术化、互相冲突的错误信息。
9. Publish failure 存在 `No image`、空白图、图片加载失败等情况。
10. 多平台发布结果、计划状态与失败恢复仍需使用同一业务事实。

---

# 2. 产品目标

本轮目标：

1. 将 Create Pins 生命周期状态与 Plan 工作视图区分开。
2. 让用户无需离开 Create Pins 即可快速查看和操作 Weekly Plan。
3. 确保 Scheduled Pin 在执行时真正使用排程时保存的发布平台、账号和目标。
4. 为新内容提供合理的默认发布目标，同时禁止 Settings 改动影响历史排程。
5. 清除 Unscheduled / In Plan / Scheduled 等重复概念。
6. Failed 页面始终提供可理解的图片、原因和下一步操作。
7. 所有客户界面彻底移除 `No image`、raw provider error 和重复错误。
8. 保持 AI 创建入口明显，但避免 Create Pins 变成工具按钮集合。

---

# 3. 非目标

本轮不做：

* 新建第二套 Pin entity
* 新建独立 Plan Pin entity
* 新建第二套 Schedule 时间字段
* 重做 Social Account credential 模型
* Facebook / Instagram 新的多账号架构
* 账号级团队 ACL
* 把 Board 管理加入 Social accounts
* 自动把失败内容迁移到其他账号
* 自动使用 Workspace default 替换失效的 Scheduled destination
* 新建独立 Failed Pins 页面
* Production 部署

# 4. Create Pins 信息架构

## 4.1 Lifecycle navigation

顶部内容状态只保留：

```text
All
Unscheduled
Scheduled
Posted
Failed
```

移除：

```text
Plan
```

原因：

`Unscheduled / Scheduled / Posted / Failed` 描述 Pin 生命周期。

`Plan` 描述用户工作的方式和页面视图。

二者不能继续作为同一层级状态。

# 6. 移除重复的 “Added to plan · assign a date”

当前 Plan 下方：

```text
Added to plan · assign a date
```

客户很难理解它与：

```text
Unscheduled Pins
```

有什么业务区别。

本 PRD 推荐取消这一客户概念。

未确定发布时间的内容统一视为：

```text
Unscheduled
```

Plan 侧边栏可以显示其中符合 Plan 条件的内容：

```text
Needs scheduling
```

但这只是 Unscheduled 的一个 Plan 工作队列，不创建新的 lifecycle state。

禁止形成：

```text
Draft
Unscheduled
Added to Plan
Plan Unscheduled
```

四种相似客户状态。

如果现有代码存在 `plan membership` 数据，Audit 必须先解释其业务必要性。

不得直接删除数据字段。

---

# 7. Unscheduled Pins 数据语义

## 7.1 Canonical 定义

Unscheduled Pins 必须满足：

```text
该 Pin 当前仍是 draft / unscheduled
AND
没有有效 scheduledAt
AND
没有完成 publish
AND
不是当前 unresolved publish failure
```

同一个 Pin ID：

* 已 Scheduled → 不出现在 Unscheduled
* 已 Posted → 不出现在 Unscheduled
* Publish failed → 进入 Failed
* Generation failed → 进入 Failed

不得因为图片相同而判断为同一个 Pin。

判断依据必须是 Pin identity / lifecycle state。

---

## 7.2 已发布内容出现在 Unscheduled

当前截图中已经出现该问题。

必须 Audit：

* Unscheduled query
* Plan sidebar query
* Posted query
* cache
* client filtering
* server filtering

禁止通过前端：

```text
filter(status !== "posted")
```

临时遮盖错误，而底层 canonical query 仍不一致。

# 8. Scheduled Pin 的多平台发布规则

这是本 PRD 的核心数据规则。

## 8.1 不采用“所有 Connected 平台自动发布”

仅仅因为某个平台 Connected，不代表客户想让每条内容都发布到该平台。

因此：

```text
Connected accounts
≠
selected publish destinations
```

禁止默认向所有已连接 Social Accounts 自动发布。

---

# 9. Default Publishing Destinations

在：

```text
Settings
→ Publishing
```

增加：

```text
Default publishing destinations
```

这是发布偏好，不是 Social Account 管理。

示例：

```text
Default publishing destinations

✓ Pinterest
  @VibePin Home

✓ Instagram
  @vibepin.co

✓ Facebook Page
  VibePin

Apply these destinations to new Pins and new schedules by default.
```

用户可以修改。

---

## 9.1 Default 的含义

Default publishing destinations 只能：

> 为新内容预填选项。

它绝不能：

* 修改已有 Draft 的 destination
* 修改已有 Scheduled Pins
* 修改 Plan 中已确定目标的内容
* 修改 Failed Retry 的原目标
* 修改历史 Posted 内容
* 在 Job 执行时充当 fallback

---

# 10. Schedule 时冻结发布目标

用户点击：

```text
Schedule
Update schedule
Smart Schedule
Add to Plan（如流程仍保留）
```

时，必须保存确定的 publish destinations。

概念至少包含：

```text
social_account_id
destination_id
platform
account snapshot
destination snapshot
```

Pinterest：

```text
Pinterest Account
→ Board
```

Instagram：

```text
Instagram Account
```

Facebook：

```text
Facebook Page
```

具体 schema 等待 Audit，不要求直接创建上述字段名。

---

## 10.1 Settings 修改不能影响历史 Schedule

例如：

星期一：

```text
Pin A
Pinterest Account A
Board X
Instagram Account A
Facebook Page A
```

星期二用户修改 Settings default。

星期三 Pin A 执行时仍必须使用星期一保存的目标。

禁止读取：

```text
current workspace default
recently used account
newly connected account
current Settings selection
```

---

# 11. Multi-platform execution

一条 Scheduled Pin 到达发布时间：

```text
Pin
├── Pinterest destination
├── Instagram destination
└── Facebook destination
```

每个 destination 独立执行并独立记录结果。

可能产生：

```text
Pinterest      Published
Instagram      Published
Facebook       Failed
```

客户详情必须能看到这种真实情况。

---

## 11.1 Pin overall lifecycle

推荐：

全部目标成功：

```text
Posted
```

存在至少一个 unresolved publish failure：

```text
Failed
```

Failed detail 同时保留已经成功的平台信息。

失败目标 Retry 成功后：

```text
Failed
→ Posted
```

不创建第二个客户可见 Pin。

# 12. Pinterest Board 记忆

当前问题：

用户已经选择：

```text
Pinterest Account A
Board：家居
```

下一次创建或排程时又完全为空。

体验成本过高。

---

## 12.1 推荐方案

为每个 Pinterest Account 保存：

```text
last used Board preference
```

这是用户体验偏好，不是 Pin 的发布事实。

例如：

```text
Account A → last used Board：家居
Account B → last used Board：Living Room
```

---

## 12.2 新 Pin

创建新的 Pin 时：

如果系统预选 Account A：

可以预填：

```text
Board：家居
```

前提：

* Board 仍存在
* Board 仍属于 Account A
* 用户仍有发布权限

否则保持为空。

---

## 12.3 当前 Pin 中切换 Account

这是安全边界。

用户在编辑当前 Pin 时：

```text
Account A
Board：家居
```

改为：

```text
Account B
```

必须：

```text
立即清除 Board
```

不得静默自动选 Account B 的 last-used Board。

可以在 dropdown 中提示：

```text
Recently used: Living Room
```

但必须由用户确认。

---

## 12.4 Settings 边界

Social accounts 仍然不承担 Board 管理。

本轮不在：

```text
Settings → Social accounts
```

加入：

* Default Board
* Board list
* Board sync
* Board diagnostics

Default publishing accounts 属于：

```text
Settings → Publishing
```

Board 选择仍主要属于实际内容发布工作流。

# 13. Failed 图片规则

核心原则：

> 客户界面不允许出现 `No image`。

也不允许：

* broken image
* 空白蓝灰块
* 无限 onError
* 技术图片 URL
* 图片请求错误文字

---

# 14. Publish failure 图片

Publish failure 的含义是：

> 最终内容已经存在，只是发布过程失败。

因此首选图片必须是：

```text
当时准备发布的最终图片
```

禁止默认使用失败占位图代替真实内容。

建议视觉：

```text
真实 Pin 图片
+
Publish failed badge
```

可以使用轻微 dark overlay，但不得让图片失去可辨认性。

不建议把所有 Publish failed 图片强制变成黑白。

用户需要看见：

> 到底是哪张图发布失败了。

---

# 15. Publish failure 图片 fallback

解析顺序：

```text
final publish image
→ persisted draft image
→ source image
→ product image
→ parent image
→ cached/local safe fallback
→ generic failed thumbnail
```

只有前面所有来源均不可用，才进入最后 fallback。

最后 fallback 使用统一灰度视觉：

```text
generic Pin thumbnail
+
failure icon
```

但不得写：

```text
No image
```

这类 fallback 同时应产生内部 diagnostic，方便后续修复真正的数据问题。

---

# 16. Generation failure 图片

Generation failure 没有最终 AI result。

依次使用：

```text
source image
→ Product image
→ Style reference
→ parent image
→ safe local fallback
→ AI generation failure thumbnail
```

同样禁止 `No image`。

---

# 17. Failed UI 简化

当前错误存在：

* 同一卡片多次重复说明
* 泛化原因过长
* 技术原因直接暴露
* Banner + card + toast 同时重复
* Publish failure / Generation failure 表达混乱

统一成：

```text
[Publish failed]

Pinterest couldn't publish this Pin.
Review the Pin and try again.

[Edit] [Retry]
```

# 35. 发布反馈改为异步任务模型

当前多平台发布存在明显的重复反馈问题：

```text
先显示 Pinterest Published
→ 等待
→ 再显示 Pinterest / Instagram / Facebook Published
→ 同时出现多个 Toast
```

这会让客户误以为系统重复发布，或者无法判断哪一次才是最终结果。

新的产品规则：

> Publish action 与 Publish result 必须分开。

---

## 35.1 用户点击 Publish now 后

用户点击：

```text
Publish now
```

系统首先完成：

```text
创建 canonical publish job
→ 保存本次 publish destinations
→ 创建/确认各 destination publish task
→ 返回 accepted
```

一旦 VibePin 已经可靠接受任务，不要求客户继续停留在 Drawer 等待 Pinterest / Instagram / Facebook Provider 完成。

即时反馈只出现一次：

```text
Publishing started
Results will update automatically.
```

或者等价的简洁客户文案。

禁止此时显示：

```text
Published successfully
```

因为 job accepted 不等于 Provider 已经发布成功。

---

## 35.2 Publish CTA 状态

点击后按钮可以短暂进入：

```text
Starting…
```

canonical publish job 创建成功后：

```text
Publishing
```

不得为了等待全部 Provider 返回而让整个 Drawer 长时间处于 blocking loading。

客户可以：

* 关闭 Drawer
* 切换页面
* 继续其他操作

发布任务继续执行。

## 35.4 Toast 规则

同一次 publish operation：

```text
最多显示一个即时 Toast
```

推荐：

```text
Publishing started

```

禁止：

```text

```

随后再出现：

```text

```

随后再出现：

```text

```

这种连续 Toast。

多个平台结果必须收敛到 `Publish results`。

## 35.5 最终完成后

如果用户仍停留在当前详情中：

Publish results 自动更新即可。

不要求再次弹 Toast。

如果未来需要全局通知能力，可以单独设计：

```text

```

但不属于本轮 MVP 必需范围。

# 36. Publish result 的 canonical 状态

必须明确区分：

```text
accepted
publishing
published
failed
```

语义：

### accepted

VibePin 已可靠创建 publish job 并保存 destination。

### publishing

Provider 发布任务正在执行。

### published

Provider 已返回明确成功结果，并保存：

```text
external_post_id
external_post_url
published_at
```

或对应平台可验证的成功事实。

### failed

该 destination 当前发布失败，需要恢复操作。

禁止：

```text
job 创建成功
=
Published
```

也禁止：

```text
HTTP request 已发送
=
Published
```

# 37. 删除全局 View Pin

多平台发布后：

```text
View Pin
```

语义已经不成立。

必须删除 Drawer 底部全局：

```text
View Pin
```

改成 destination 自己的操作：

```text
View on Pinterest
View on Instagram
View on Facebook
```

只有：

```text
status = published
AND
存在合法 external_post_url
```

时才显示。

# 39. Published Pin 的动作规则

已经 Published 的内容不能继续默认显示：

```text
Publish now
```

因为客户会理解为：

> 这条内容是不是还没有发出去？

Published 状态允许：

```text
View results
Edit for reuse
```

如果未来支持再次发布，必须明确使用：

```text
Publish again
```

而不是 `Publish now`。

`Publish again` 属于新的发布操作，需要重新确认 destinations。

# 44. 不允许 Publish result 闪烁成多个不同事实


客户容易认为系统又执行了一次发布。


```text

Instagram       Publishing…
Facebook Page   Publishing…
```

随后 destination 独立更新。

禁止先渲染 Pinterest-only success，再追加其他平台。

# 47. 本部分必须保护的额外原则

```text
Publish accepted ≠ Published.

Provider success 才能显示 Published。

一个 Publish operation 只给一次即时反馈。

最终结果属于 Publish results，不属于 Toast。

完整 destination list 应从发布任务开始时就确定。

多平台结果允许部分成功。

Published 内容不应继续显示 Publish now。

Schedule 时间只能有一个编辑入口。

Save changes 是 Edit Scheduled Pin 的主动作。

AI 是编辑辅助工具，不是 Edit Pin 的主 CTA。

Desktop hover 提供快速信息，但不能成为唯一信息入口。
```
