E. Synchronize Recommended References with selected References
==================================================

REVISED 2026-07-21. Supersedes the original Section E.

Background:

The previous split was intentional, not a bug: recommended Pins come from
pin_samples, and Pinterest创意智能层 PRD §4 previously forbade sending those
images to the image model, allowing only derived patternTags. That rule has
been lifted by the product owner. See Pinterest创意智能层-PRD-v0.2.md §4
(now v0.3) for the replacement rules and §4.4 for recorded risk.

New requirement:

All Reference entry points must use one shared selectedReferences collection.

Each selectedReference must carry at least:

- id
- imageUrl
- source
- sourceUrl / pinterestUrl
- title
- reason
- patternTags
- role = style_reference

When a recommended Reference is selected:

- immediately add its thumbnail to the top Style references selected tray;
- keep the lower recommendation card visibly selected;
- send its imageUrl into the generation request as role=style_reference.

Uploaded References, Saved References, prior generated images and recommended
Pins all share the same selection state, but each retains its own provenance
(source, sourceUrl, patternTags).

The generation request must distinguish roles explicitly:

  image_inputs:
    - role=product     real product subject, preserved in the output
    - role=reference   Pin inspiration, guides scene/composition/style only

(The wire value emitted by /api/generate for a style reference is "reference";
"style_reference" is the client-side role name for the selection state. Do not
introduce a second vocabulary on the wire.)

patternTags remain an auxiliary prompt signal; they no longer substitute for
the user-selected Pin image.

Staged delivery (server constraint):

/api/generate currently IGNORES a client-supplied body.image_inputs and rebuilds
it from product_images plus a single style_ref string (buildImageInputs). One
request therefore carries at most ONE reference image. Consequently:

- Commit 1 unifies selectedReferences, preserves full provenance and completes
  two-way sync between the top tray and the recommendation cards. It must NOT
  claim that multiple recommended Pins reach the model.
- Commit 2 introduces per-Reference groups, sets each group's Reference as its
  style_ref, shares product_images across groups, and only then are real Pin
  Style Reference inputs and result association actually live.

Commits 1 and 2 are consecutive. The intermediate state must not be previewed,
deployed or delivered as a finished version.

Recommendation labelling (consumes the data session's API contract):

POST /api/reference-candidates returns recommendationBasis. Render:

- product_analysis  → "Recommended for this product"
- product_text      → "Recommended for this product"
- category_fallback → "Category inspiration"

Never label category-only results as Recommended for this product.

When deselected:

- remove it from the top selected tray;
- remove the recommendation-card selected state;
- remove it from the generation request.

Removing a thumbnail from the top selected tray must also deselect the matching
card below.

Do not maintain disconnected arrays for:

- recommended references;
- uploaded references;
- saved references;
- drawer references.

A source field may remain, but selected state must be unified.

Preserve the current maximum of 3 selected References unless repository rules
show a different approved limit.

Do not automatically select recommended References.

==================================================
G. Pins per reference (output quantity)
==================================================

REVISED 2026-07-21. Supersedes the original Section G, which required Number
of Pins to be independent from Reference count. The existing production
multiplication behavior is CORRECT and is retained.

Rule:

  totalPins = max(selectedReferences.length, 1) × pinsPerReference

Examples:

- 0 References, quantity 3 → 3 Pins
- 1 Reference,  quantity 3 → 3 Pins
- 2 References, quantity 3 → 6 Pins
- 3 References, quantity 3 → 9 Pins

UI requirements:

- when at least one Reference is selected, label the control Pins per reference;
- when no Reference is selected, label it Number of Pins;
- the CTA shows the resulting total, e.g. Generate 9 Pins;
- show the calculation near the CTA, e.g. 3 references × 3 Pins each;
- the CTA must update immediately when the selector or Reference set changes.

Request structure (precise):

  groupRequestCount = pinsPerReference
  groupCount        = max(selectedReferences.length, 1)
  totalPins         = groupCount × pinsPerReference

- totalPins governs ONLY the batch CTA, the placeholder count and the final
  record total.
- each Reference group issues its own /api/generate call with
  count = pinsPerReference.
- the groupCount requests together produce totalPins.
- never request totalPins in a single call and assign References afterwards.

pinsPerReference is limited to 1, 2 or 3. The maximum batch is therefore
3 References × 3 Pins each = 9 Pins.

Serial execution (mandatory):

/api/generate holds a per-user "active-generation" TTL lock and returns HTTP
429 (error_type user_generation_limit) for a concurrent second call. Reference
groups must therefore run as a serial queue:

- create all totalPins placeholders up front;
- call /api/generate once per Reference group, strictly sequentially;
- update that group's placeholders as soon as it returns;
- on group failure, continue with the next group;
- do not remove, weaken or bypass the existing single-user generation lock;
- show batch progress, e.g. "Generating reference 2 of 3".

placeholders, success records and failure records must all reconcile to
totalPins. Do not maintain separate unsynchronized count states.

K. Failed Pin media fallback
==================================================

Create Pins → Failed must never show:

- No image;
- broken-image icon;
- empty gray media block;
- solid blue block;
- blue gradient failure art.

Publish failure media priority:

1. final imageUrl / generatedImageUrl;
2. mediaAssetId-resolved final asset;
3. persisted draft final image;
4. sourceImageUrl;
5. linked Product main image;
6. local bundled fallback image.

Publish failure should normally display the exact final image that was prepared
for Pinterest.

Generation failure media priority:

1. valid partial generation result;
2. sourceImageUrl;
3. sourceAssetId-resolved image;
4. parentDraftId / parent asset;
5. Product main image;
6. selected Reference image;
7. local bundled fallback image.

Expected behavior:

- Product generation failure → Product original image.
- Reference-based generation failure → original Reference.
- Regeneration failure → parent/current draft image.
- Prompt-only failure with no image → local bundled fallback.

If no suitable asset exists, use an existing neutral Pin placeholder or add a
local bundled asset such as:

/public/images/pin-image-fallback.svg

The fallback must:

- be a neutral image-style 2:3 visual;
- not simulate a real product;
- not depend on an external URL;
- ship in the production build;
- use alt text: Pin image unavailable.

Implement a finite fallback chain:

- each candidate URL attempted at most once;
- onError advances to the next candidate;
- no infinite loop;
- never rewrite a failed URL back into src.

Do not rely on transient:

- blob URLs;
- object URLs;
- localhost URLs;
- expired signed URLs.

Reuse the existing server asset resolver for protected/signed media.

Preserve existing media relationships through:

- refresh;
- re-login;
- cross-device;
- Retry publish;
- Move to Unscheduled;
- Plan → Create Pins navigation.

Maintain distinct actions:

Publish failure:
- Retry publish;
- Edit;
- Move to Unscheduled;
- Delete.

Generation failure:
- Try again / Regenerate;
- Edit;
- Delete.

Both may share one media fallback resolver, but not one failure state machine.
