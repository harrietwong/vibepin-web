# VibePin Batch Video Pin P0 Implementation Plan

## Scope And Frozen Decisions

- The implementation base must be the deployment task's clean, tested integration HEAD derived from frozen Preview `f585e17f` plus the accepted AI Copy v2 commits. Replace `DEPLOYMENT_INTEGRATION_HEAD` with that exact SHA before Task 1.
- Work only in `codex/video-pin-p0-0916` in an isolated worktree. Never edit the dirty main checkout.
- Do not push, deploy, apply migrations, mutate any external database or bucket, refresh Pinterest tokens, or make a real Pinterest publish request.
- `VIDEO_PIN_UPLOAD_ENABLED=false` is the server gate. `NEXT_PUBLIC_VIDEO_PIN_UPLOAD=false` is the client gate. Flag-off behavior stays image-only and unchanged.
- Batch semantics are fixed: selecting N videos creates at most N independent Pin drafts, one video per draft. Videos are never combined into an image carousel or a multi-video Pin.
- A batch accepts at most 20 files. Each file is at most 100 MiB. Accepted containers are MP4, M4V, and MOV. Duration must be 4 seconds through 5 minutes. These limits are centralized constants and returned as stable validation codes.
- Batch upload has item-level `queued | uploading | succeeded | failed | cancelled` states and aggregate `completed | partial | failed | cancelled` states. Successful items are never rolled back because a sibling fails. Retrying a batch retries failed items only and must not duplicate successful drafts.
- Upload concurrency is two. Cancel stops queued work, keeps already-created drafts, and attempts to abort the in-flight request. If the storage client cannot abort an in-flight upload, completion is reconciled and the orphan is removed or placed in the durable cleanup outbox.
- Draft video binaries stay in private `generated-private` storage. Never return or persist a public Supabase URL. Reads require authentication plus exact owner/bucket/path provenance.
- The video object path is owner-scoped and compatible with v76 materialization. Client-supplied `userId`, object path, lifecycle, checksum, and ready state are never trusted.
- Browser-observed duration, dimensions, and poster extraction are UX evidence only until server/provider validation. MIME/container and byte size are verified against the stored object before provenance becomes ready.
- The P0 poster is extracted locally from the video near one second and uploaded through the existing secured private-image path. If poster extraction fails, the video draft remains usable but AI Copy enters a clearly labelled `video_cover_unavailable` degraded mode.
- AI Copy v2 analyses the extracted poster plus user/product metadata only. It must display that it used the cover frame and must not claim to understand motion, audio, speech, or the entire video.
- Pinterest video publishing uses the VibePin production-verified protocol: register media, multipart upload without bearer authorization, poll media to `succeeded`, then create a Pin with `source_type: "video_id"`, the returned `media_id`, and `cover_image_key_frame_time: 1`.
- Do not implement `cover_image_url` for videos. A future custom cover may use controlled `cover_image_data`, but it is outside P0.
- Scheduling does not register Pinterest media early. Registration and upload happen only when the destination is claimed for immediate or due execution because the presigned Pinterest upload URL is short lived.
- Any network timeout after provider work may have started becomes durable `delivery_unknown`. It is never converted to an ordinary retryable failure and never blindly resent.
- Reuse v75 private media provenance and cleanup, and v76 publish intent/assets/delivery items/provider attempts. Do not create a second publish ledger or write those tables directly from clients.
- The legacy Python publisher must explicitly reject video unless it is upgraded to the exact same protocol; it may not silently route a video through the image path.

## Contract Types

```ts
type ContentMediaKind = "image" | "video";

type VideoContentMedia = {
  id: string;
  kind: "video";
  url: string;              // protected app URL, never a public bucket URL
  objectPath: string;
  mimeType: "video/mp4" | "video/x-m4v" | "video/quicktime";
  fileSizeBytes: number;
  durationMs?: number;      // browser-observed in P0
  width?: number;
  height?: number;
  posterUrl?: string;
  posterObjectPath?: string;
  source: "upload";
  altText: string;
};

type BatchUploadItemState = "queued" | "uploading" | "succeeded" | "failed" | "cancelled";
type VideoBatchState = "completed" | "partial" | "failed" | "cancelled";

type VideoBatchResult = {
  batchId: string;
  state: VideoBatchState;
  total: number;
  completed: number;
  failed: number;
  cancelled: number;
  items: Array<{
    clientIndex: number;
    fileName: string;
    state: BatchUploadItemState;
    draftId?: string;
    requestId?: string;
    errorCode?: string;
  }>;
};
```

For each successful file, `contentId === draft.id`, `media.length === 1`, `media[0].kind === "video"`, and `coverMediaId === media[0].id`. `imageUrl` remains a compatibility alias to `posterUrl` when a poster exists; it must never point to the video binary.

## Task 2: Build Private Direct Video Upload And Finalization

**Owner:** bounded implementation worker, then independent task reviewer.

**Primary files:**

- New server upload-intent/finalize modules under `web/src/lib/server/media/`
- New authenticated routes under `web/src/app/api/studio/video-upload/`
- New client helper under `web/src/lib/studio/`
- Extend, do not weaken, v75 provenance/cleanup helpers

**Behavior:**

- Auth happens before Storage or database access.
- Prepare accepts a bounded list of file descriptors and one batch idempotency key, allocates owner-scoped random paths, stores server-owned pending items, and returns short-lived signed upload capabilities. Tokens are not persisted or logged.
- The browser uploads each binary directly to private Storage with `upsert:false`; video bytes never pass through the ordinary Next multipart image route.
- Finalize verifies exact owner/path, actual stored size, actual content type, and ISO-BMFF `ftyp` signature via a bounded range read before registering ready provenance.
- Empty, oversized, mismatched, missing, expired, cross-owner, replay-conflicting, and malformed objects fail closed with stable codes.
- Failed finalization removes the object; removal failure enters the durable cleanup outbox. Duplicate finalize returns the original result.
- Add `/api/storage-media` for authenticated range-capable video reads. It reuses exact provenance and path authorization, rejects `failed/unresolved`, streams only allowed video MIME within the cap, sets private cache, `Vary`, and `nosniff`, and supports video range requests without exposing raw bucket URLs.

**TDD:** Route/module tests cover 401-before-side-effects, batch bounds, MIME/size/signature checks, owner isolation, upload/finalize idempotency, cleanup compensation, safe range responses, and token redaction. No real Storage or database calls.

## Task 6: Implement The Pinterest Video Adapter

**Owner:** integration-capable implementation worker, then independent task reviewer.

**Primary files:**

- `web/src/lib/server/pinterest/pinMediaSource.ts`
- `web/src/lib/server/pinterest/service.ts`
- `web/src/lib/server/pinterest/publishPin.ts`
- New injectable video upload/poll helper

**Behavior:**

- Register with Bearer and `{media_type:"video"}`.
- Upload all Pinterest-provided fields plus the file last as multipart to the returned S3 URL, without Authorization, requiring HTTP 204.
- Poll with injected clock/sleep until `succeeded`, explicit provider failure, or configurable deadline.
- Create with `video_id`, the same-account `media_id`, and `cover_image_key_frame_time:1`; never send `cover_image_url`.
- Return bounded provider evidence: media id, Pin id/URL, request/RID when safe, stage, and classification. Never return tokens, upload parameters, presigned URLs, or provider bodies.
- Classify definite pre-dispatch validation/4xx failures separately from network/5xx/timeout states that may be unknown.

**TDD:** Mock the adapter boundary, not Pinterest internals. Verify headers, multipart field set/order, 204 requirement, polling transitions/deadline, exact create body, successful evidence, token consistency, redaction, and failure-versus-unknown classification. Never call Pinterest.

## Task 7: Bind Immediate And Scheduled Video Publishing To v76

**Owner:** high-judgment implementation worker, then independent task reviewer.

**Primary files:**

- New v76 server wrapper under `web/src/lib/server/publish/`
- Publish confirmation receipt/media contracts
- `web/src/app/api/pinterest/pins/route.ts`
- `web/src/app/api/cron/publish-due/route.ts` and due logic
- Legacy Python publisher explicit video rejection or identical adapter support

**Behavior:**

- Confirm/prepare freezes draft/content/source revision/media/destination identity before provider work.
- Materialize and claim each destination/item through existing v76 leases and RPCs. Video uses private provider-bytes delivery; no permanent public copy or stored signed URL.
- Immediate and due paths call the same adapter and settlement code.
- Pinterest media registration occurs only after a ready destination claim, never when merely scheduling.
- Start a durable provider attempt before registration. Settle success/failure/unknown before returning. A 201 Pin response is success and is never resent.
- A timeout or process-loss window after provider dispatch becomes `delivery_unknown`; replay/retry is rejected until reconciliation proves the outcome.
- One failed/unknown destination does not overwrite a sibling's success. Future schedules and out-of-time worker runs do not claim or call the provider.
- Old image behavior remains compatible and old routes cannot bypass `materialization_required` for video.

**TDD:** Extend PGlite and route/service tests first. Cover lease competition, all-items-ready gate, attempt idempotency, crash after create-before-settle, unknown anti-retry, due/future selection, partial destinations, source revision conflict, owner tampering, and legacy bypass attempts.
